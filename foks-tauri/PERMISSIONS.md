# FOKS desktop: the resolved permission posture

Audited against `gen/schemas/acl-manifests.json` and `gen/schemas/capabilities.json`
as generated by `tauri-build` 2.6.3 / `tauri` 2.11.5 on this tree. Re-run
`cargo check -p foks-desktop-app` and re-read those files whenever `tauri` moves;
this document records what the schema *says*, not what the permission names
suggest.

## What the capability grants

`capabilities/default.json` scopes to the single window `main` and lists three
entries, each naming one command:

```
core:event:allow-listen
core:event:allow-unlisten
core:window:allow-start-dragging
```

Those three resolve to exactly three invocable commands, and that resolution is
a test rather than a claim: `the_resolved_capability_reaches_only_those_three_commands`
in `src/lib.rs` walks `tauri-build`'s own generated projection —
`gen/schemas/capabilities.json` expanded through `gen/schemas/acl-manifests.json`
— and asserts the result is precisely

```
core:event|listen
core:event|unlisten
core:window|start_dragging
```

| Permission | Why the renderer needs it |
| --- | --- |
| `core:event:allow-listen` | `dragdrop.rs` emits `foks://drop-hover` and `foks://drop-paths` **from Rust** to the `main` window. `src/bridge.ts` subscribes with `listen` from `@tauri-apps/api/event`; without this the drop zone has no hover state and a drop reports nothing. |
| `core:event:allow-unlisten` | The other half of the same subscription: `listen` resolves to an unlisten function, and `bridge.ts` calls it on unmount. Granting listen without unlisten leaks a handler per mount. |
| `core:window:allow-start-dragging` | The command Tauri's own injected `data-tauri-drag-region` script calls to move the window under an overlay title bar (`titleBarStyle: "Overlay"`, `hiddenTitle: true`). It moves this app's own window and can do nothing else. The frontend does not mark a drag region today; the grant is kept because the window is configured for one, and it is pinned by an exact-set test rather than assumed. |

`emit` and `emit_to` are deliberately **absent**. Every event in this app
travels one way — Rust observes a native drag and tells the window — so the
renderer has nothing to emit. Granting emit would let script in that window
synthesise a `foks://drop-paths` event; the drop-path allowlist in
`commands.rs` already refuses a path Rust never observed, and withholding emit
means the forgery cannot be attempted in the first place.

## What the capability does **not** grant

`core:default` used to be the first entry. It is a **permission set**, not
"nothing else": it expands to nine sub-defaults and 92 individual commands.
Replacing it removed all of them. The ones that mattered:

| Was reachable through | Commands dropped |
| --- | --- |
| `core:image:default` | `from_path` **read any file the webview named**, bounded by nothing in the ACL, in an application whose whole design keeps file bytes out of the renderer. Also `new`, `from_bytes`, `rgba`, `size`. |
| `core:webview:default` | `internal_toggle_devtools` — an inspector over a window that renders secrets — plus `get_all_webviews`, `webview_position`, `webview_size`. |
| `core:path:default` | Eight path *string* commands (`resolve`, `resolve_directory`, `normalize`, `join`, `dirname`, `extname`, `basename`, `is_absolute`). No filesystem access — that lives in `tauri-plugin-fs`, which is not a dependency — but FOKS composes no paths in the renderer either. |
| `core:menu:default` | 22 menu-construction commands. FOKS builds no menu from JS. |
| `core:tray:default` | 12 tray commands. |
| `core:app:default` | `version`, `name`, `tauri_version`, `identifier`, `bundle_type`, and the listener registry. FOKS answers all of this through its own `app_info` command. |
| `core:window:default` | 28 read-only window queries plus `internal_toggle_maximize`, the double-click-titlebar behaviour. If double-click-to-maximize is ever wanted, add `core:window:allow-internal-toggle-maximize` deliberately — see below — rather than restoring the set. |
| `core:resources:default` | `close` on resource-table handles. |
| `core:event:default` | `emit` and `emit_to`, alongside the listen/unlisten that were kept. |

Two things about that list are worth keeping straight, because the earlier
version of this document got one of them wrong:

- **Whether a command is compiled in is not the security boundary.** The tray
  commands are `#[cfg(all(desktop, feature = "tray-icon"))]`
  (`tauri-2.11.5/src/lib.rs:112`) and this crate does not enable `tray-icon`,
  so they are not registered in a Cargo build of this package. That is a
  property of *this crate's feature set*, and Cargo unifies features across a
  workspace while Bazel resolves them per target: a sibling in the same build
  that wants `tray-icon` can make them present again without touching this
  file. The same holds for `internal_toggle_devtools`, which is
  `#[cfg(all(desktop, any(debug_assertions, feature = "devtools")))]`
  (`tauri-2.11.5/src/webview/plugin.rs:180,253`) and is therefore compiled into
  every debug build. Feature unification decides what exists; the capability
  decides what the webview may call. Only the second is a control, and it is
  the one asserted by test.
- **Compiled-but-ungranted is inaccessible.** With those permissions gone from
  the capability, `invoke('plugin:image|from_path', …)` is refused by the ACL
  before the command runs, whether or not `core:image`'s commands are in the
  binary. That is the guarantee; "the feature is off" is not.

Also absent, and for the same reason:

- **No notification permissions.** AKA's capability lists four
  (`notification:default`, `allow-notify`, `allow-request-permission`,
  `allow-is-permission-granted`); FOKS links neither `tauri-plugin-notification`
  nor `notify-rust`.
- **No plugin permissions at all.** `tauri-plugin-dialog` and
  `tauri-plugin-clipboard-manager` are registered in `run()` and their webview
  APIs are unreachable: `dialog:default` (`allow-message`, `allow-save`,
  `allow-open`) and `clipboard-manager`'s permissions are absent, so
  `invoke('plugin:dialog|open')` and `invoke('plugin:clipboard-manager|read_text')`
  are refused. Both plugins are driven **from Rust** — the save-destination
  picker, the import/replace picker, and the copy-with-clear — which is the
  point: the webview asks for the operation, but never receives a native-picked
  source path or file contents. `tauri-plugin-single-instance` has no webview
  API at all.
- **No filesystem, shell, http or fs-scope permissions.** Those plugins are not
  dependencies.

Custom commands are a separate surface: `generate_handler!` commands are not
ACL-gated, so the FOKS command list in `lib.rs` is the *whole* remaining IPC
surface, and it is bounded by `require_unlocked` and `require_main_window`
rather than by a capability file.

## The controls that actually bound a value-returning command

Phase 1 has none — `agent_status` and `app_info` return no secret. When
Phase 2's `read_item` lands, the controls are, in order:

1. `applock::require_unlocked` at the top of every value-bearing command.
2. The native navigation policy in `src/navigation.rs`, so the window that may
   call these commands is only ever on FOKS's own origin.
3. The CSP `script-src 'self'` in `tauri.conf.json`.
4. This capability set.
5. `withGlobalTauri: false`, so the IPC surface is not published on a global
   object in a window that renders secrets.
6. One command returning one item at one version.

The first control is armed at process start whenever the operating system can
authenticate the desktop user. The renderer must read `app_lock_state` and
complete `unlock_app` before it loads agent or catalog data. A platform that
reports authentication unavailable starts unarmed so the UI cannot become
permanently inaccessible.

`read_item` is that sole value-returning command. `copy_item_value` performs
the same exact-version read but writes directly to the system clipboard;
`download_file` sends bounded exact-version chunks directly to a native-picked
destination. Neither returns content through IPC.

All Phase 3 mutation commands also call `require_unlocked`. A dropped source
path is accepted only when Rust observed a native event containing that one
UTF-8 path, and it is consumed once; multi-file drops authorize nothing. A
renderer cannot use the path-taking command as a general local file reader.
Rust rejects symlinks and non-regular sources and sends contents
to the local agent through bounded streaming frames. Native picker paths do not
cross IPC at all. Secret text and link targets necessarily arrive as mutation
arguments, are moved into zeroizing storage immediately, and are never echoed
in a response or log.

`require_main_window` in `src/commands.rs` is **defence in depth and not a
control**. FOKS has one window, so the label check discriminates nothing that
script already running in that window could not pass. It is kept, and pinned by
a test, so that adding a second window is a deliberate act.

## Where the window may be

`src/navigation.rs` registers a plugin whose `on_navigation` hook answers a
pure allowlist of whole origins — scheme, host and effective port compared
exactly, never by prefix:

| Origin | Packaged | Development |
| --- | --- | --- |
| `tauri://localhost` | allow | allow |
| `http://tauri.localhost`, `https://tauri.localhost` | allow | allow |
| `http://127.0.0.1:1421` | deny | allow |
| everything else | deny | deny |

`tauri://localhost` is what Tauri serves the embedded bundle from on macOS and
Linux; the `tauri.localhost` pair is wry's workaround form on Windows and
Android, allowed so that adding a target — or turning on `useHttpsScheme` —
is not a silent blank window. Everything else is refused: remote origins,
`file:`, `data:`, `blob:` and `javascript:` as a top-level destination, a
hostless URL, and any scheme Tauri did not register. A refusal cancels the
navigation and leaves the current page where it was; it logs scheme, host and
port, never a path, query or fragment, because those are attacker-chosen and a
window that renders secrets can put a value in one.

Whether the development origin is allowed is `tauri::is_dev()` —
`!cfg!(feature = "custom-protocol")` — and **not** `debug_assertions`, because
that feature is the same switch `tauri`'s own `get_app_url` reads when it
chooses between `build.devUrl` and the embedded bundle. This package declares
no `custom-protocol` feature, so `cargo build --release` still produces a
binary that loads the Vite server; `debug_assertions` would deny that binary
its own start page. The distributable artifacts do turn the feature on — Bazel
through `MODULE.bazel`'s crate annotation, `tauri build` through the CLI — and
those are exactly the builds where `http://127.0.0.1:1421` is refused.

The CSP is the second line for the same boundary, not the first: `form-action
'none'`, `base-uri 'none'`, `object-src 'none'`, `frame-src 'none'` and
`frame-ancestors 'none'` close the mechanisms CSP does cover, but CSP does not
reliably govern every top-level navigation. `connect-src` is deliberately not
spelled out; `default-src 'self'` already governs it, and the effective policy
each packaged platform ends up with should be captured before that directive
is made more explicit.

New windows are refused today by the runtime, because no `on_new_window`
handler is installed and the config-declared window is the only one. Obtaining
that hook would mean replacing the config-created window with a manually built
one — a much larger lifecycle and packaging change — so it is left as it is
rather than half-done.

## Clipboard platform difference

macOS copies include `org.nspasteboard.ConcealedType`, which asks cooperating
clipboard-history tools not to retain the value. Linux has no equivalent hint:
clipboard managers can capture it, and X11 selection ownership can disappear
with the process. Linux therefore clears after 15 seconds instead of 30;
shutdown waits for one best-effort clear before exiting. Prefer Download for
long-lived file content. An unpacked Linux archive or AppImage also cannot
install the polkit action, so app lock reports unavailable there rather than
offering a lock that cannot be opened; the `.deb` installs it.

## The permission decision, and how it is kept

`core:default` was retained through the Phase 2 review and replaced here. The
allowlist is the three entries above and nothing else. The reasoning:

- **An explicit list has to be re-audited on every `tauri` bump. That is the
  feature, not the cost.** The set it replaced expanded silently: three lines
  in a file, 92 commands at runtime, including a webview-named file read. A
  hard-coded list cannot grow without a diff.
- **Two tests hold the line.** One compares the source capability against the
  exact expected array — an added entry, a dropped entry, a duplicate, a
  reordering or a second window scope all fail — and names
  `core:default`, `core:image:*`, `core:menu:*`, `core:tray:*`, `core:path:*`,
  `core:webview:*`, `core:app:*`, `core:window:default`, `core:event:default`,
  `core:event:allow-emit` and `core:event:allow-emit-to` individually, so the
  diff that restores one fails on a name a reviewer recognises. The other
  resolves the *generated* projection through the ACL manifests and asserts the
  three command identifiers. It compares identifiers, never descriptions, so a
  Tauri documentation change cannot make it noisy and a Tauri permission-set
  change cannot make it quiet.
- **Bazel feature unification must not be mistaken for the control.** See the
  two notes above: whether `tray-icon` or `devtools` happens to be enabled in a
  given build decides what is *compiled*, not what the webview may *call*. The
  capability is the control, and the Bazel-built macOS artifact resolves the
  same three commands as the Cargo build because both read this same file.

If the double-click-titlebar maximize interaction turns out to be required, the
addition is `core:window:allow-internal-toggle-maximize`, one line, driven by
that acceptance requirement — not `core:window:default`, and not `core:default`.
