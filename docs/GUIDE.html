How FOKS Keeps Your Keys

An architectural and cryptographic guide to the Federated Open Key Store: dual wire protocols, post-quantum hybrid public keys, Patricia Merkle epoch DAGs, resident daemon isolation, desktop endpoint security, and upstream Go compatibility.

Open Questions & Active Engineering

This implementation addresses several strict protocol and systems boundaries currently active in the codebase:

  • Epoch 65,536 Canonicality Ceiling: At epoch 65,536, the DAG backpointer sequence reaches 16 elements, forcing an array16 MessagePack encoding that triggers an upstream Go v0.1.9 signable validator rejection. The Merkle engine explicitly enforces this ceiling with EpochLimitExceeded.
  • Server Expiry Cleanup Plan: SQLite schema version 45 introduces 7 targeted partial indexes across expiring reservations, challenges, view tokens, and log sends to prevent unbounded database degradation under high turnover.
  • Basic Chat Retention & Storage Isolation: Each rt_messages row permanently stores two 1 MiB encodings (the submitted envelope and the returned message) without compaction or per-team quotas. Work is underway to isolate chat storage from core identity and KV storage.
  • Terminal Chat Operation Compaction: Local client hard state accumulates permanent terminal chat_operations and chat_submissions rows. Bounded replay evidence is being designed to allow pruning without creating replay vulnerabilities.
  • Endpoint Security Support: Desktop application lock integrates native biometrics on macOS (LocalAuthentication) and Linux (PolicyKit D-Bus authority). Windows remains unsupported due to unverified named-pipe ACL primitives.

1. What we are trying to do

The Federated Open Key Store (FOKS) is a zero-knowledge, end-to-end encrypted secret store, distributed file system, and real-time team collaboration platform. Its purpose is to allow individuals, teams, and autonomous AI agents to store secrets, synchronize key-value data, and exchange encrypted messages across federated hosts without placing trust in any server infrastructure.

Traditional cloud key management systems treat the server as an authoritative, trusted entity that decrypts master key material or acts as a gatekeeper. If the server infrastructure is compromised, subpoenaed, or maliciously operated, stored secrets are exposed, and history can be silently manipulated. FOKS eliminates this vulnerability through a set of strict architectural invariants:

  • Zero Server Trust: The server is treated as an untrusted, Byzantine storage relay and sequencing engine. It holds only public identity commitments, opaque encrypted parcels, and signed Merkle tree roots. The server never learns private seeds, plaintext secret entries, directory paths, or message cleartext.
  • Local Cryptographic Verification: Every client endpoint independently verifies all cryptographic evidence. State transitions, team memberships, and directory mutations are authenticated via Ed25519 or P-256 signatures, compressed Patricia Merkle proofs, and hash chains before being admitted to local storage.
  • Decoupling Authority from Secrecy: Governance (who has permission to modify a team or identity) is completely separated from confidentiality (who can decrypt data). Mutating a team requires an append-only signature chain; reading team secrets requires possessing a generational unsealing key.
  • Forward Secrecy via Generational Seeds: When a device is revoked or a team member is removed, the identity advances to a new key generation. All subsequent data is encrypted under fresh generational keys. The evicted party is cryptographically prevented from reading future history, while legitimate members traverse backward seed chains to access past records.
  • Post-Quantum Resistance: All public key encapsulation combines classical elliptic curves with NIST ML-KEM-768 (formerly Kyber-768), ensuring that encrypted data captured today cannot be decrypted by future quantum computers ("Harvest Now, Decrypt Later").

2. Architecture & The Dual Wire Protocol

The FOKS architecture is divided into three distinct operational tiers: client frontends, a resident client daemon, and untrusted server relays. To balance desktop developer ergonomics with extreme cryptographic rigor, FOKS employs a Dual Wire Protocol design.

Client applications—such as the React 18 desktop interface, the CLI, and the Model Context Protocol (MCP) server—never interact with the network directly, nor do they touch long-term private key material or SQLite databases. Instead, they communicate locally with foks-agent, a resident background daemon.

Protocol 1: Local Length-Prefixed JSON IPC

Frontends connect to foks-agent over a private Unix domain socket (defaulting to foks-rs.sock beneath the configured state directory). The framing is deliberately simple and robust:

  • Framing Envelope: A 4-byte big-endian unsigned integer specifies the exact byte length of the UTF-8 JSON message that follows.
  • Size Constraints: Messages are strictly capped at MAXIMUM_MESSAGE_BYTES = 1 MiB (1,048,576 bytes). Requests exceeding this limit are refused immediately before reading the full payload.
  • Envelope Budget: To prevent JSON encoding drift, exactly FRAME_ENVELOPE_RESERVE_BYTES = 32 KiB is reserved for metadata (correlation IDs, status tags, path strings, and operation parameters). This leaves exactly 1,015,808 bytes for payload content.
  • Base64 KV Payloads: Binary blobs (such as file uploads and downloads) travel as base64-encoded strings. A plaintext payload of MAXIMUM_KV_PAYLOAD_BYTES = 700 KiB (716,800 bytes) expands to 955,738 base64 bytes, which fits comfortably within the budget with 60,070 bytes of headroom.
  • Socket Security & Permissions: On Unix, the daemon checks socket metadata on bind and connect. It verifies that the socket and state directory are owned by rustix::process::geteuid() and that permissions are restricted to 0o600 or 0o700 (rejecting group/world access). The daemon also checks the peer process credentials on every accepted connection, refusing any client whose effective UID does not match the daemon's UID.
  • Process Mutual Exclusion: The daemon acquires an exclusive fs2::FileExt::try_lock_exclusive() on .foks-rs.lock. If another instance is already running, startup terminates immediately with an address-in-use error.

Protocol 2: Remote Canonical Snowpack RPC

Communication between foks-agent and foks-server occurs over TLS 1.3 (TCP port 4430). The transport uses MessagePack RPC framing containing strongly-typed, canonical Snowpack payloads:

  • Canonical Snowpack vs MessagePack: While ordinary MessagePack allows arbitrary map key orderings and flexible integer encodings, Canonical Snowpack enforces strict determinism: map keys must be sorted lexicographically by their encoded bytes, integers must be encoded using the shortest possible byte representation, and empty collections must follow strict canonical forms.
  • Cryptographic Hashability: Because canonical Snowpack guarantees that identical logical objects produce byte-for-byte identical binary encodings, clients and servers can compute cryptographic hashes directly over serialized bytes. Domain separation is enforced using 64-bit typed prefixes (e.g., LINK_OUTER_V1_TYPE_ID, MERKLE_NODE_TYPE_ID, KV_ROOT_BINDING_PAYLOAD_TYPE_ID).
  • Untrusted Transport: Even if TLS is terminated by an enterprise proxy or intercepted by an attacker, the integrity of the data is completely protected by the inner Snowpack signatures and Merkle proofs. The server cannot tamper with records without invalidating their mathematical commitments.

3. Cryptographic Foundations & Key Families

Security in FOKS is built on modern, quantum-resistant, and formally specified cryptographic primitives. Every identity, file, and permission is bound to explicit mathematical structures rather than implicit database associations.

Hybrid Encryption Public Keys (HEPK)

Traditional public key encryption relies on Diffie-Hellman over elliptic curves (such as Curve25519 or NIST P-256). While secure against current classical computers, these algorithms are vulnerable to Shor's algorithm running on large-scale quantum processors. To protect users against long-term data capture and retroactive decryption, FOKS requires Hybrid Encryption Public Keys (HEPK) across all user and team identities.

Defined in foks_proto::identity::hepk, an HEPK combines two distinct public keys:

pub struct Hepk {
    pub classical: DhPublicKey, // Curve25519 ([u8; 32]) or P256 ([u8; 33])
    pub mlkem768: Vec<u8>,     // NIST ML-KEM-768 encapsulation key (1,184 bytes)
}

When encrypting a secret parcel for a device (such as a generational PUK or PTK parcel), the sender performs a dual encapsulation:

  1. Classical Agreement: The sender generates an ephemeral curve keypair and computes a classical shared secret via X25519 ECDH (for software devices) or P-256 ECDH (for YubiKey hardware tokens).
  2. Post-Quantum KEM: The sender executes the NIST ML-KEM-768 encapsulation algorithm against the recipient's ML-KEM public key, yielding a 1,088-byte post-quantum ciphertext and a post-quantum shared secret.
  3. Hybrid Secret Derivation: The classical and post-quantum shared secrets are concatenated alongside domain separation tags and passed into SHA-512/256 (or HKDF). The resulting 32-byte master seed is used to encrypt the payload via XSalsa20-Poly1305.

To decrypt, an attacker would have to break both the discrete logarithm problem on elliptic curves and the module learning-with-errors (MLWE) lattice problem. If either primitive remains secure, the plaintext remains unreadable.

Hardware Security: YubiKey PIV Integration

For high-assurance deployments, FOKS supports hardware tokens via the YubiKey PIV (Personal Identity Verification) interface. Implemented in foks-yubi, the system delegates signing and unsealing operations to smartcard hardware without exposing private key bytes to host RAM:

  • Slot Architecture: PIV slots 0x82 through 0x95 (SlotId::MIN = 0x82, SlotId::MAX = 0x95) are allocated for FOKS credentials.
  • Signing Slot: Configured for ECDSA over NIST P-256 with SHA-256. Signs host-chain links, Merkle commitments, and device authentication challenges.
  • Unsealing Slot: Uses ECDH over NIST P-256. Because physical YubiKeys currently lack native on-chip ML-KEM acceleration, FOKS implements an authenticated hybrid subkey bridge: the YubiKey's hardware ECDH derives an intermediate master seed, which in turn deterministically derives the ML-KEM-768 keypair and delegates local cryptographic operations.

Generational PUK and PTK with SeedChainBox

FOKS manages user vaults via a Per-User Key (PUK) and team vaults via a Per-Team Key (PTK). To enforce forward secrecy, these keys are strictly generational. Each generation Gk is represented by an independent, randomly sampled 32-byte seed.

When an existing device is revoked or a team member is demoted or removed, the remaining authorized members advance the generation from Gk to Gk+1. The server receives newly encrypted parcels for the active members under their HEPKs. However, current members still need to decrypt historical files and messages encrypted under older generations.

FOKS solves this with SeedChainBox recursion (defined in foks_proto::key_material):

pub struct SeedChainBox {
    pub generation: u32,
    pub role: KeyRole,
    pub secret_box: BoxEnvelope, // Encrypted seed G_(k-1) under G_k
}

Inside generation Gk's parcel, a SeedChainBox contains the seed for generation Gk-1 encrypted under the seed of Gk using XSalsa20-Poly1305. An active member possessing Gk can recursively unwrap the chain backwards: Gk → Gk-1 → Gk-2 → … → G1. However, an evicted member holding only Gk-1 has no mathematical pathway to derive Gk, guaranteeing forward secrecy.

KV KeySet and Vault Derivation

The generational seed is never used directly to encrypt user files or directory metadata. Instead, the client invokes derive_key(seed, app_index, context) using HKDF-SHA256. For key-value vault operations, application index 5 derives the kv_app key, which splits into a two-part KV KeySet (defined in foks_crypto::KvKeySet):

  • Subkey 1 (MAC Key): A 32-byte Zeroizing key used exclusively with HMAC-SHA256 to authenticate the KvRoot structure. It binds the root directory ID, directory version vector, team/user party ID, and key generation into a cryptographic tag (KV_ROOT_BINDING_PAYLOAD_TYPE_ID). The server cannot forge or tamper with the root pointer.
  • Subkey 2 (Box Key): A 32-byte Zeroizing key used with XSalsa20-Poly1305 (24-byte nonce, 16-byte Poly1305 authenticator). It encrypts directory seeds (DIR_KEY_SEED_TYPE_ID), directory entries (dirents), small file payloads (SMALL_FILE_PAYLOAD_TYPE_ID), and chunked file blocks.

Local Keystore Encryption

Private device seeds, PUK seeds, and account metadata must be persisted locally between agent restarts. The foks-keystore crate encrypts all local credentials using XChaCha20-Poly1305 with domain separation AAD b"foks-keystore-record-v1" and magic header b"FOKSKS\0\x01".

The master encryption key is managed through platform-native secure credential stores:

  • macOS: Stored as a generic-password item in the user's macOS Keychain (login keychain).
  • Linux: Stored via the FreeDesktop Secret Service D-Bus API in the default collection using encrypted peer-to-peer session keys.
  • File Fallback: Where desktop keyrings are unavailable (e.g. headless servers or CI runners), FOKS generates an owner-restricted master key file (0o600 permissions) via create_master_key_file.

4. Secrecy Chain vs Authority Chain

The defining architectural insight of FOKS is the complete decoupling of the Secrecy Chain (confidentiality) from the Authority Chain (integrity and governance). In naive designs, identity and encryption are tangled: signing keys are conflated with decryption keys, or server access tokens grant read access to records. FOKS treats these as two orthogonal, independently verifiable chains.

The Secrecy Chain: How Data is Read

The Secrecy Chain operates top-down from device private keys to cleartext secrets:

  1. The local device activates its private unsealing key (Curve25519/P-256 private key and ML-KEM-768 decapsulation key) from the OS keystore.
  2. The client fetches the latest encrypted PukParcel or PtkParcel from the server.
  3. The device unseals the parcel, recovering the 32-byte generational seed Gk.
  4. If the user is accessing historical records, the client reads the nested SeedChainBox structures to recursively unwrap older generation seeds (Gk-1, Gk-2, …).
  5. From the appropriate generation seed, the client derives the application key (index 5) to produce the KvKeySet.
  6. The MAC key verifies the integrity of the server's directory root, and the Box key decrypts the directory seed and dirent metadata.
  7. Finally, individual file chunks are decrypted in memory using XSalsa20-Poly1305. Plaintext is never written to unencrypted disk caches.

The Authority Chain: How History is Mutated

The Authority Chain operates bottom-up from device signatures to Merkle roots and client pins:

  1. To perform an action (e.g., provision a device, rotate a PUK, add a team member, or revoke credentials), an authorized device constructs a strongly-typed link structure (e.g., LinkOuterV1).
  2. The link contains the target party ID, the action payload, the sequence number k, and the cryptographic hash of the previous link (prev_link_hash). This forms an immutable, append-only hash chain.
  3. The acting device signs the link with its Ed25519 or P-256 private signing key. Where required, stacked signatures are appended (e.g., a founding owner countersignature or YubiKey subkey proof).
  4. The signed link is submitted to foks-server. The server updates its compressed Patricia Merkle tree, inserting or updating the leaf node corresponding to the user or team ID with the hash of the new chain tail.
  5. The server increments the Merkle epoch E, computes the new root node hash RE, generates the epoch DAG backpointers, and signs the epoch head using its delegated host Merkle key.
  6. When clients synchronize, they verify the server's signed Merkle root, validate the presence proof connecting the Merkle root to the user's chain tail, and check the sequential link signatures.
  7. Upon successful validation, foks-client-db advances its local anti-rollback pin in SQLite. If the server ever attempts to present an older epoch or a conflicting fork, the client detects the sequence regression and halts immediately.

5. Compressed Patricia Merkle Trees & The Epoch DAG

To enable thousands of lightweight clients to verify identity states, team memberships, and public keys without downloading entire transaction ledgers, FOKS employs a Radix Compressed Patricia Merkle Tree coupled with an Epoch Directed Acyclic Graph (DAG).

Patricia Merkle Tree Architecture

Implemented in crates/foks-merkle-store, the tree is a deterministic, authenticated key-value dictionary mapping 32-byte keys (e.g. hashed user IDs or team IDs) to 32-byte values (the hash of that entity's current chain tail). Every node is represented by one of two variants (defined in foks_merkle_store::node):

  • Leaf Nodes (Node::Leaf): Tagged with byte b"1" (discriminant 0). Contains the 32-byte key and 32-byte value. The node hash is computed using typed domain separation: prefixed_hash_signable(MERKLE_NODE_TYPE_ID, ...).
  • Interior Nodes (Node::Interior): Tagged with byte b"0" (discriminant 1). Contains:
    • prefix_bit_start: The starting bit offset of the common path in the 256-bit key space.
    • prefix_bit_count: The length of the shared prefix in bits.
    • prefix: A byte vector storing the shared prefix bit slice.
    • left: 32-byte hash of the left child (branching on bit value 0).
    • right: 32-byte hash of the right child (branching on bit value 1).

By collapsing non-branching paths into interior nodes via radix prefix compression, the tree remains extremely compact. A proof of presence (or proof of absence) consists of a short list of sibling hashes and prefix slices along the path from the root to the target leaf, allowing clients to verify an identity in sub-millisecond time.

Epoch DAG Backpointers and Skip-List Advance

Each mutation on the server increments the global Merkle epoch E. Rather than maintaining a simple linear list of historical roots, FOKS links epochs into a DAG using a logarithmic skip-pointer sequence. Defined in foks_merkle_store::history::back_pointer_sequence(epoch), an epoch commits to prior epoch roots at power-of-two backward distances:

// For epoch E, backpointers step backwards by powers of 2:
// Pointers = [E - 1, E - 2, E - 4, E - 8, E - 16, ...]
pub fn back_pointer_sequence(epoch: u64) -> Vec<u64> {
    let mut pointers = Vec::new();
    let mut step = 1u64;
    while step < epoch {
        pointers.push(epoch - step);
        step <<= 1;
    }
    pointers
}

When a client that last verified epoch 992 connects to a server at epoch 998, it does not need to download and verify the six intermediary trees. Instead, it invokes collect_roots(992, 998). Using the skip-pointer graph, the client traverses logarithmic jumps (e.g., 998 → 997, 998 → 996, 996 → 994, 994 → 992) and cryptographically proves that epoch 998 is a strict, unbroken descendant of epoch 992 in O(log N) steps.

The Go v0.1.9 Boundary Guard (Epoch 65,536 Ceiling)

The FOKS Rust implementation maintains bug-for-bug wire compatibility with the reference Go v0.1.9 implementation (github.com/foks-proj/go-foks). This strict requirement revealed a critical boundary condition at epoch 65,536.

The mathematical and encoding conflict arises as follows:

  1. Skip Pointer Count: At epoch 65,536 ($2^16$), the number of backpointers in back_pointer_sequence(65536) reaches exactly 16 elements (indices 16 through 31).
  2. MessagePack Array Encoding: In MessagePack format, an array of up to 15 items is encoded as a fixarray (byte range 0x90 to 0x9f). An array of 16 items can no longer fit in a fixarray; the go-codec serializer switches to the 3-byte array16 format (byte 0xdc followed by 0x00 0x10).
  3. Upstream Go Validator Bug: The signable canonical validator in Go v0.1.9 contains an overzealous check designed to reject non-minimal encodings. However, due to an off-by-one boundary flaw, the validator rejects any array16 header whose element count could fit in earlier structures—and erroneously flags length 16 as an illegal encoding!
  4. Unrecoverable Failure: Consequently, any Go v0.1.9 node attempting to serialize or verify epoch 65,536 crashes with an unresolvable canonical validation error.

To prevent corrupting state or diverging from upstream nodes, crates/foks-merkle-store/src/history.rs enforces an explicit ceiling:

pub const MAX_CANONICAL_MERKLE_EPOCH: u64 = 65_536;

pub fn back_pointer_hash(...) -> Result<[u8; 32]> {
    if (16..=31).contains(&pointers.len()) {
        return Err(Error::EpochLimitExceeded);
    }
    // ...
}

If a tree reaches epoch 65,536, the Rust engine refuses to emit the broken array16 payload, failing closed with Error::EpochLimitExceeded. The server returns a structured MERKLE_VERIFY_ERROR, preserving database integrity until a synchronized upstream protocol upgrade can be deployed.

6. The Client Daemon Stack

The client side of FOKS is built around three collaborating layers: foks-agent (the resident service daemon), foks-client / foks-client-app (the protocol execution engine), and foks-client-db (the persistent local database).

The Resident Daemon: foks-agent

To avoid requiring every CLI invocation or UI window to independently initialize SQLite connections, unlock OS keyrings, and synchronize network Merkle anchors, foks-agent runs as a long-lived resident daemon. Owned by the operating system user, it maintains exclusive ownership of client credentials and database locks.

The daemon architecture enforces strict operational boundaries:

  • Exclusive Lockfile (.foks-rs.lock): During startup in --state-dir, the daemon opens .foks-rs.lock with O_NOFOLLOW, verifies that the file is owned by the current UID with mode 0o600, and calls fs2::FileExt::try_lock_exclusive(). If another process holds the lock, startup aborts immediately.
  • Socket Hygiene: The Unix domain socket (foks-rs.sock) is protected against race conditions and stale socket hijacking. Before binding, the daemon inspects the path; if a socket exists, it verifies that the socket is owned by the current UID with mode 0o600, tests whether a live agent is responding, and removes stale sockets atomically. A SocketGuard struct records the socket's device and inode numbers, ensuring that an exiting agent never deletes a successor's socket.
  • Peer Authentication: Every accepted connection checks rustix::process::geteuid() against the peer process credentials. Connections from different UIDs are rejected immediately.
  • Bounded Worker Semaphore: Background jobs and incoming RPC requests execute through a bounded concurrency semaphore. Requests carry cancellation deadlines that propagate into the synchronous network client. If an operation times out, the local connection is closed because the durable network outcome may be ambiguous.
  • Bootstrap vs Ready Mode: If a state directory lacks initialized credentials, the daemon enters a restricted Bootstrap Mode. In this state, it accepts only AgentStatus and InitializeState requests; all data access attempts fail with BootstrapRequired. Once master credentials are generated or imported, the daemon moves atomically to Ready mode and starts background synchronization.

Durable Storage: foks-client-db (Schema v39)

Durable client state is managed by foks-client-db, an embedded SQLite store that enforces strict cryptographic monotonicity. The database is strictly partitioned into Hard State and Soft State.

Hard State

The hard-state database uses SQLite application ID 0x464F_4B53 (ASCII 'FOKS') and schema version 39. It stores only cryptographically verified, immutable evidence. Private device seeds and PUK seeds are explicitly excluded and stored in the encrypted keystore.

In a single atomic transaction, the hard-state store commits:

  • Discovery name to permanent HostID cryptographic pin.
  • Exact authenticated host-chain bytes and indexed chain tails.
  • Active delegated service endpoints (Merkle, Identity, Realtime, KV).
  • Latest signed Merkle root bytes, indexed epoch, and root node hash.
  • Flat trusted-local Merkle checkpoints.
  • Verified user/team chain links and public device/PUK HEPK records.

The database layer enforces monotonicity checks as defense-in-depth: it rejects lookup-name identity substitutions, chain rollbacks, Merkle epoch regressions, and same-sequence forks. Even if a compromised server presents conflicting data, SQLite transactions fail closed.

Soft State

Soft state is maintained in a separate SQLite database file. It acts as an accelerated caching and staging layer:

  • Stores complete verified KV directory trees, dirent versions, and content projections.
  • Reconstructs path-version vectors for fast kvCacheCheck RPC synchronization.
  • Stages large-file plaintext in bounded chunk rows. Incomplete staging chunks from crashed processes are invisible to normal readers and safely reclaimed during maintenance passes.

7. The Desktop Application & Endpoint Security

The FOKS desktop interface provides an enterprise-grade graphical experience built on modern web standards and native operating system integration.

Frontend & Tauri Architecture

The desktop stack consists of a React 18 + Vite application (located at apps/desktop/src) running inside a Tauri v2 native shell (apps/desktop/src-tauri):

  • Design Tokens: The user interface is styled using a dedicated tokenized design kit (apps/desktop/kit) supporting dark/light system adaptation, fluid typography, and accessible component states.
  • Detached Daemon Lifecycle: When the desktop application launches, it spawns foks-agent with detached standard streams. The desktop shell does not hold a child process handle; closing or reloading the UI window leaves the daemon running undisturbed, preserving active network leases and background sync.

AppLock: Hardware Biometrics & Polkit

To prevent unauthorized access to local vaults when a workstation is unattended, FOKS implements AppLock runtime access control. Implemented in apps/desktop/src-tauri/src/applock.rs, all value-returning IPC commands are gated by an atomic lock generation:

  • macOS Biometrics: Leverages the Apple LocalAuthentication framework (via objc2_local_authentication). The desktop evaluates LAPolicy::DeviceOwnerAuthenticationWithBiometrics, prompting the user for Touch ID, Apple Watch confirmation, or the system account password.
  • Linux PolicyKit (Polkit): Connects to the system D-Bus authority (org.freedesktop.PolicyKit1) at interface /org/freedesktop/PolicyKit1/Authority. The desktop queries and evaluates action org.foks.desktop.unlock (defined in org.foks.desktop.policy), displaying the native system authentication dialog.
  • Zero Account Password Storage: FOKS never prompts for or stores master passwords. Authentication is entirely delegated to the host operating system.
  • Generation Gating: When locked, the lock generation increments, immediately invalidating the in-memory catalog cache, closing web-admin windows, and concealing active chat messages.

Real-Time Chat Notification Consumer & The Active Thread Invariant

The desktop chat subsystem (located in apps/desktop/src/chat/notification-consumer.ts) synchronizes team channels, unread indicators, and message banners in the background.

Because querying dozens of team channels can exhaust server capacity or introduce latency, the consumer implements an adaptive backoff schedule governed by the Active Thread Invariant:

const FALLBACK_MS = 5000;       // 5 seconds base interval
const FALLBACK_MAX_MS = 60_000;  // 60 seconds maximum backoff
  • The Invariant: The currently viewed, active channel never backs off from FALLBACK_MS (5 seconds), regardless of how long it has been quiet. Because the user is looking directly at that conversation, staleness is unacceptable.
  • Adaptive Backoff for Quiet Channels: Unviewed, background channels double their polling interval on each pass that discovers no new messages (5s → 10s → 20s → 40s → 60s max).
  • Instant Reset: As soon as a read operation discovers a new incoming message in any channel, that channel's polling interval is immediately reset to the base 5-second interval.

Real-Process Chat Benchmark

The chat pipeline is continuously verified using a real-process benchmark that executes compiled release Rust agent and server binaries alongside desktop TypeScript services. Driving a sustained load of 6 incoming messages per second with concurrent foreground history reads and message writes, Linux x86_64 testing produces the following p95 latency results:

These measurements reflect the complete end-to-end service, agent IPC, network RPC, and database transaction path.

8. Server Architecture, Transaction Engine & Federation

The FOKS server (crates/foks-server) is designed as a stateless, high-throughput network engine built on Axum and Tower, backed by an authoritative SQLite persistence layer (crates/foks-server-db).

The Single-Writer SQLite Transaction Actor

SQLite provides exceptional performance when configured correctly, but concurrent write transactions in multi-threaded servers can encounter lock contention (SQLITE_BUSY). FOKS completely eliminates write contention using an actor-based architecture:

  • Single Dedicated Writer: The database is opened in WAL (Write-Ahead Logging) mode. Exactly one dedicated background OS thread owns the write connection and holds an adjacent filesystem lock.
  • MPSC Channel Queuing: All mutating RPC endpoints (user signup, link submission, Merkle root advancement, message sends) send transactional closures across a bounded Tokio MPSC channel to the writer actor. Mutations execute sequentially and commit atomically.
  • Read Connection Pool: Concurrent read operations (Merkle queries, parcel downloads, public key lookups) execute through a separate pool of read-only SQLite connections. Because SQLite WAL mode permits readers to proceed concurrently with the writer without blocking, read latency remains predictable regardless of write volume.

Modular Database Schemas

The server's storage layout is divided into specialized SQL schema modules (located in crates/foks-server-db/src/schema/):

  • core.sql: Server settings, host identification, TLS certificates, and service capabilities.
  • identity.sql: User accounts, usernames, device registrations, public HEPKs, and PUK parcels.
  • team.sql: Named and ad-hoc team definitions, member roles, and PTK parcels.
  • kv.sql: Key-value roots, directory metadata, and version vector allocations.
  • realtime.sql: Real-time channels, memberships, inbox sequences, and message rows (rt_messages).
  • team_invitations.sql: Shareable invitation certificates, pending requests, and RSVP decisions.
  • sso.sql: OpenID Connect enterprise sessions, verification flows, and authorization assertions.

Enterprise OIDC Federation

FOKS integrates with corporate identity systems via OpenID Connect (OIDC). Using foks-oidc, users can authenticate using corporate Single Sign-On (Google Workspace, Okta, Microsoft Entra ID). The server verifies the IdP's signed JWT tokens and validates email domain claims.

However, conforming to the zero-knowledge threat model, the IdP never learns or derives vault encryption keys. SSO acts purely as an identity verification mechanism; vault decryption remains strictly gated by the user's local device private keys or HESP recovery phrases.

The Server Threat Model

FOKS defines a rigorous, mathematically enforced threat model specifying exactly what the server can and cannot observe or manipulate:

What the Server CAN See & Do What the Server CANNOT See or Do
Can observe public account usernames, hostnames, and device IDs. Cannot read secret plaintext: Personal and team passwords, API tokens, and files are end-to-end encrypted.
Can observe the size and timing of encrypted parcels and network requests. Cannot inspect directory trees: Directory names, file paths, and metadata are encrypted under KvKeySet.
Can sequence Merkle epochs and publish signed root commitments. Cannot read message content: Real-time chat messages travel inside encrypted XSalsa20-Poly1305 envelopes.
Can enforce rate limits and refuse malformed or unauthenticated requests. Cannot forge identity links: Mutating an account or team requires valid Ed25519/P-256 signatures from authorized devices.
Can track channel membership counts and inbox sequence numbers. Cannot rewind history undetected: Client databases pin the latest seen Merkle epoch and reject rollback attempts.

9. Human Recovery & Out-of-Band Pairing (HESP)

A fatal flaw in many end-to-end encrypted systems is the recovery mechanism: users either rely on memorable (and easily guessed) passwords, or they are forced to store fragile paper seed phrases that fail when partially obscured. FOKS introduces Human-Exact Secret Phrases (HESP) for root recovery and device pairing.

203-Bit Backup Recovery Key

When an account is founded, the client generates a 203-bit root recovery secret (defined in foks_crypto::backup). This secret is encoded into exactly 17 tokens, alternating between standard BIP-39 English words and precise numbers:

BACKUP_SEED_BYTES    = 26 (203 bits entropy, top mask 0x07)
BACKUP_PHRASE_TOKENS = 17 tokens:
  - 9 BIP-39 words   (11 bits each = 99 bits entropy)
  - 8 numbers        (13 bits each, range 0..8191 = 104 bits entropy)
  Total entropy      = 99 + 104 = 203 bits

The interleaved word-number structure serves three vital purposes:

  1. Grammatical & Visual Cadence: Alternating words and numbers (e.g., apple 4092 zebra 1842 …) drastically reduces human transcription errors compared to uniform word lists.
  2. Immunity to Dictionary Attacks: The 104 bits of numeric entropy completely break standard natural language cracking dictionaries and language-model predictors.
  3. Argon2id PPE Stretching: Passphrase-Protected Encryption (PPE) combines the HESP secret with Argon2id key stretching, ensuring resistance against high-speed GPU or ASIC offline cracking.

From this 203-bit secret, FOKS derives an account recovery signing key and a recovery unsealing key. A public recovery box is registered on the server. Whenever active devices rotate the PUK to a new generation, they re-encrypt the new seed under the public recovery key. If all physical devices are destroyed, the user enters the 17-token phrase, reconstitutes the recovery keys, unseals the latest PUK parcel, and provisions a replacement device.

125-Bit Key Exchange (KEX) Pairing

Provisioning a second device (such as adding a laptop when an enrolled smartphone is present) uses an ephemeral 125-bit KEX Secret (defined in foks_crypto::kex):

KEX_SEED_BYTES    = 16 (125 bits entropy, top mask 0x1f)
KEX_PHRASE_TOKENS = 13 tokens:
  - 7 BIP-39 words  (11 bits each = 77 bits entropy)
  - 6 numbers       (8 bits each, range 0..255 = 48 bits entropy)
  Total entropy     = 77 + 48 = 125 bits

The user initiates pairing on Device A, which displays the 13-token phrase. Device B enters the phrase. The two devices establish an authenticated out-of-band encrypted channel over the server relay. Device A verifies Device B's newly generated HEPK, wraps the current PUK seed, signs a new device provisioning link, and commits the mutation to the Authority Chain. Device B is enrolled without master seeds ever leaving local memory.

10. Model Context Protocol (MCP) Integration

Modern engineering workflows increasingly rely on autonomous AI agents (such as Claude, Antigravity, and coding assistants). Giving AI agents raw database credentials or unencrypted filesystem access creates severe security liabilities. FOKS provides a dedicated Model Context Protocol (MCP) daemon (crates/foks-mcp) that allows AI models to interact safely with encrypted vaults over standard JSON-RPC 2.0 stdio.

Tool Surfaces: KV & Team

The MCP server exposes two specialized toolsets (defined in foks_mcp::contract):

  • KV Toolset: Gives agents structured tools to inspect and modify encrypted vaults:
    • list: Lists files and directories with pagination (PAGE_ROWS = 1000).
    • get: Fetches file content up to MAX_FILE_BYTES = 4 MiB.
    • stat: Retrieves file metadata, sizes, and version vectors.
    • put: Encrypts and writes new files (payloads up to MAX_INPUT_BYTES = 8 MiB).
    • mkdir, rm, mv: Directory creation, atomic removal, and renaming.
  • Team Toolset: Inspects organization and access status:
    • usage: Reports storage consumption and quota boundaries.
    • list-memberships: Queries all personal and team vaults accessible to the agent profile.
    • team-list: Enumerates active team members and cryptographic roles.

Durable Write Recovery with fennec_submission_id

LLM tool calls frequently experience network timeouts, process terminations, or context truncations. In naive implementations, retrying a timed-out write can create duplicate files or trigger race conditions.

FOKS solves this via Durable Write Recovery:

pub struct SubmissionArgs {
    pub fennec_submission_id: String,
}

Every mutating tool call accepts an optional client-supplied idempotency key (fennec_submission_id). When foks-agent executes the write, it records the submission ID in SQLite alongside the transaction outcome. If an AI agent times out or crashes, it can invoke fennec_status or fennec_pending upon restarting. The agent learns whether the prior write succeeded, failed, or is still in flight—guaranteeing exactly-once execution semantics without manual intervention.

11. Upstream Go v0.1.9 Compatibility & Differential Testing

FOKS is not an isolated implementation; it is designed to run in mixed environments alongside the reference Go implementation (github.com/foks-proj/go-foks@v0.1.9). To guarantee zero drift and absolute wire compatibility, the repository includes an extensive differential testing framework.

The Reference Oracle: tools/foks-v019-oracle

Located at tools/foks-v019-oracle, this tool wraps the unmodified Go v0.1.9 codebase. It connects to live hosts (e.g. foks.app:4430) or replays test transcripts to emit immutable Canary Fixtures (stored under crates/foks-snowpack/tests/fixtures/foks-v0.1.9/):

  • probe-response.snowp: Exact canonical Snowpack probe response containing host identity, CA certificates, and signed Merkle root.
  • user/: Authenticated user chains, eldest links, second-device provisioning, revocation links, and generational PUK rotations.
  • signup/: Software registration requests, username reservations, and hidden location commitments.
  • user-mutations/: Ad-hoc and named team creation, local-user additions, demotions, and PTK rotations.
  • yubi/: YubiKey PIV mock bus fixtures, delegated Ed25519 subkeys, and triple-signature stacks.

Differential Testing & The foks-snowpack Engine

During testing, the Rust test suite loads these binary fixtures, parses them using foks-snowpack, re-serializes them, and verifies that the resulting bytes match the Go oracle byte-for-byte. Key properties verified include:

  • Lexicographical Map Ordering: Keys must be sorted by raw binary bytes rather than UTF-8 string sorting rules.
  • Minimal Integer Sizing: Positive and negative integers must occupy the smallest valid MessagePack representation (e.g. posfixint → uint8 → uint16 → uint32 → uint64).
  • Prefixed Signable Hashing: The Rust verifier (crates/foks-verify) computes hashes using identical 64-bit domain separation prefixes, ensuring that signatures verified in Rust match those generated in Go.

The Rotated Invitation Signature Quirk

Differential testing uncovered an upstream cryptographic anomaly in Go v0.1.9's invitation verification. When verifying stacked signatures on a rotated invitation certificate, the Go implementation evaluates signatures in reverse order compared to standard chain links. Rather than breaking compatibility with existing Go servers and clients, the Rust verifier explicitly accounts for this order inversion during invitation verification.

Legacy State Ingestion: foks-go-interop

Users migrating from the Go client can transition seamlessly using crates/foks-go-interop. This crate parses legacy Go client directories, reads the encrypted foks-secrets bundle (type ID 0x8456_933b_bb8a_54ae), and imports historical SQLite state tables into the modern foks-client-db schema without re-enrolling devices.

Live Dual-Direction Integration Fleet

In addition to static fixtures, the project maintains a live, dual-direction automated integration fleet powered by Docker and PostgreSQL 17 testcontainers:

  • Direction 1 (Go Client → Rust Server): Executed by go_client_rust_live_test.go, an unmodified official Go v0.1.9 client executes signups, device provisioning, and file writes against a compiled Rust foks-server binary.
  • Direction 2 (Rust Client → Go Server): Executed by run-live-compat.sh and run-live-chat-compat.sh, the Rust client and agent execute against the reference Go server with full PostgreSQL persistence.
  • Specialized Conformance Gates: Dedicated scripts test host key rotation (run-host-rotation-compat.sh), mixed-host invitation workflows (run-invitation-compat.sh), and stdio MCP tool parity (run-mcp-compat.sh).

12. Current Work, Active Issues & Boundaries

While the core cryptographic and storage layers of FOKS are fully operational, active engineering continues across several scaling, lifecycle, and platform boundaries.

Stage 1: Basic Chat Server Retention & Quotas

Active Implementation Issue

Basic chat currently lacks per-account, per-team, and per-channel retained byte and message quotas. In crates/foks-server-db/src/schema/realtime.sql, each rt_messages row permanently stores both the submitted envelope and the returned message (permitting up to 1 MiB each). There is currently no production compaction or deletion lifecycle. A single authorized user sending large payloads could consume shared server disk capacity and interfere with unrelated host services.

Planned resolution includes enforcing strict per-team and per-channel storage quotas, reserving independent database capacity for identity and KV operations, and defining explicit retention and archival lifecycles before lifting pre-release constraints.

Stage 2: Terminal Chat Operation Compaction

In foks-client-db, prepared chat operations record state in chat_operations and chat_submissions. While sensitive payload material is cleared upon terminal completion, the hard-state rows remain indefinitely. Engineering work is underway to compact terminal operations into bounded replay evidence while ensuring that pruned identifiers cannot be maliciously replayed as fresh submissions.

Stage 3: Server Expiry Cleanup Plan (Schema v45)

To eliminate unbounded row growth from transient records, SQLite schema version 45 introduces 7 targeted partial indexes (defined in crates/foks-server-db/src/schema/expiry_indexes.sql):

  1. names_reservation_expiry: On names(expires_at) WHERE uid IS NULL. Accelerates pruning of abandoned username reservations.
  2. team_names_reservation_expiry: On team_names(team_id, expires_at) WHERE team_id IS NULL. Prunes expired team name holds.
  3. recovery_challenges_cleanup: On recovery_challenges(consumed, expires_at). Reclaims one-time recovery tokens.
  4. team_view_tokens_expiry: On team_view_tokens(expires_at). Purges expired cross-team viewing tokens.
  5. team_view_challenges_expiry: On team_view_challenges(expires_at). Cleans up pending authentication challenges.
  6. team_admin_tokens_expiry: On team_admin_tokens(expires_at). Reclaims obsolete admin authorization tokens.
  7. log_sends_created_at: On log_sends(created_at). Manages diagnostics log pruning windows.

These indexes allow recurring maintenance sweeps to execute in constant time, preventing SQLite WAL degradation during high user turnover.

What FOKS Does Not Do Yet

To maintain absolute security integrity, FOKS deliberately discloses what is currently outside its supported feature set:

  • No Windows Support: The resident agent and desktop workflows currently support macOS and Linux. Windows is unsupported because authenticated named-pipe transport and OS ACL validation are not yet implemented. Connecting across an unverified pipe on Windows would breach the local security boundary.
  • No Federated or Ad-Hoc Team Chat: Real-time messaging currently supports named teams with direct same-host user memberships only. Ad-hoc and cross-host federated team chat remain disabled until multi-host broadcast routing is finalized.
  • Deferred Extended Chat Features: Extended collaboration features—such as message edits, reactions, threaded replies, user mentions, and large binary attachments—remain disabled in production builds.
  • Merkle Epoch 65,536 Barrier: Until the upstream Go implementation fixes its signable validator canonicality bug and relaxes the array16 constraint, FOKS trees cannot advance past epoch 65,536 without causing upstream client desynchronization.
Conclusion

FOKS provides a complete, mathematically verified blueprint for sovereign secret management. By combining post-quantum hybrid cryptography, clear separation of secrecy from authority, logarithmic Merkle history verification, and strict operating system process boundaries, it establishes a key store that remains provably secure even in untrusted, hostile computing environments.
