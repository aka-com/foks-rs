Inside the FOKS Desktop App

A systems and cryptographic guide to the three-tier desktop architecture: process sandboxing, capability lockdown, host-delegated authentication, memory zeroization, state coordination, and resilient federation.

Crates: foks-desktop-app, foks-desktop
Frontend: React + TypeScript (Vite)
Protocol Version: PROTOCOL_VERSION = 29
IPC Seam: Unix Domain Socket (foks-rs.sock)
Target Platforms: macOS (WebKit, LAContext) & Linux (WebKitGTK, Polkit)

Architecture Summary

The FOKS desktop application is strictly engineered so that the browser-based webview is an untrusted presentation layer. Plaintext file bytes, SQLite vault keys, long-term private signing scalars, and master credentials never cross the IPC boundary into the webview renderer. All cryptographic authority remains sealed in a standalone native Rust daemon.

1. Trust Boundaries & The Three-Tier Process Architecture

Most desktop credential managers run as a monolithic executable where frontend web code shares memory and OS capabilities with the cryptographic engine. A single cross-site scripting (XSS) vulnerability, malicious dependency in node_modules, or webview vulnerability compromises the entire vault.

FOKS solves this by decomposing the desktop client into three isolated execution tiers with unidirectional privilege boundaries:

Tier Responsibilities and Failure Domains

  • Tier 1 — Untrusted Webview: Executes the React application inside the WebKit engine. It runs under a strict Content Security Policy (CSP), has no direct filesystem access, and cannot access native OS APIs. It holds no long-term secrets.
  • Tier 2 — Native Tauri Core (foks-desktop-app): A native Rust supervisor. It manages window chrome, handles native file drop events, talks to the OS biometric subsystem, enforces clipboard scrub timers, and arbitrates all communications with the background daemon.
  • Tier 3 — Standalone Daemon (foks-agent): A resident, headless daemon process. It holds exclusive locks on the user's state directory (ClientStateLease), maintains the SQLite database containing encrypted vault ciphertext, manages the ratchet state for team communication, and executes cryptographic signing and decryption.

Why Separate the Agent into Its Own Process?

If the desktop application UI crashes, is reloaded by the user, or is restarted during an update, cryptographic operations in progress (such as an asynchronous multi-gigabyte vault synchronization, file upload, or federation ratcheting) are not interrupted. Furthermore, external CLI tools (foks-rs) connect to the identical daemon socket without requiring the GUI shell to be open.

2. Tauri v2 Security Posture & ACL Lockdown

By default, a new Tauri application exposes a rich suite of host commands to JavaScript and injects the global object window.__TAURI__. In FOKS, this default configuration is treated as an unacceptable security liability.

Elimination of window.__TAURI__

In apps/desktop/src-tauri/tauri.conf.json, the desktop explicitly sets:

{ "app": { "withGlobalTauri": false, "security": { "csp": "default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; script-src 'self'; form-action 'none'; base-uri 'none'; object-src 'none'; frame-src 'none'; frame-ancestors 'none'" } } }

Setting withGlobalTauri: false guarantees that window.__TAURI__ is never defined in the DOM global scope. The only way to send messages over the Tauri IPC bridge is through bundled JavaScript modules that statically import @tauri-apps/api/core during compilation with Vite.

The Minimal Capability Allowlist (3 Commands Only)

Tauri v2 uses an Access Control List (ACL) system defined in JSON capabilities. Standard Tauri ships with core:default, which activates 9 capability sets containing 92 individual commands. FOKS completely purges core:default and grants exactly 3 core commands in capabilities/default.json:

Command Name Permission String System Justification
core:event|listen core:event:allow-listen Allows the main window to listen to unidirectional push notifications emitted from Rust (e.g. foks://drop-hover, foks://drop-paths, foks://agent-connection-loss).
core:event|unlisten core:event:allow-unlisten Enables React components to unsubscribe from event listeners upon unmounting, preventing memory leaks.
core:window|start_dragging core:window:allow-start-dragging Required by Tauri's data-tauri-drag-region to support window dragging across the custom borderless macOS/Linux title bar.

Why Were 89 Default Commands Stripped?

The standard capability set includes core:image:default, which exposes core:image|from_path — allowing the webview to read arbitrary filesystem paths without permission checks. It also includes core:webview:default, exposing internal_toggle_devtools which could allow malicious scripts to inspect DOM memory. Dropping these closes critical exfiltration surfaces.

Third-Party Plugin Isolation

While foks-desktop-app links against tauri-plugin-dialog and tauri-plugin-clipboard-manager, zero permissions are granted to the webview for either plugin. Webview attempts to call invoke('plugin:dialog|open') fail instantly at the Tauri ACL gate. File pickers and clipboard operations can only be initiated by trusted Rust code.

Defending Custom Commands

Custom commands registered via tauri::generate_handler! bypass the plugin ACL. FOKS defends them programmatically using two universal gatekeepers:

  1. require_main_window(&webview): Inspects webview.label() and aborts if it is not "main". This prevents auxiliary webviews (such as isolated administration frames) from invoking vault commands.
  2. require_unlocked(&app): Asserts that the desktop application lock is disengaged before executing any value-bearing operation.

3. Agent Daemon Supervision & Socket Security

The native desktop application discovers or spawns the background foks-agent daemon and establishes communication over a local Unix domain socket.

Endpoint Resolution Hierarchy

The desktop determines the agent socket address via agent::resolve_endpoint with the following precedence:

  1. CLI argument: --agent-socket <PATH>
  2. Environment variable: FOKS_AGENT_SOCKET
  3. Default managed state directory: ~/.local/share/foks/foks-rs.sock (Linux) or ~/Library/Application Support/FOKS/foks-rs.sock (macOS).

Crash Directory Trust Boundary

When an explicit socket path is passed via CLI or environment variable, FOKS sets managed_crash_directory: None. Custom socket targets are treated as external trust boundaries; FOKS will not create or supervise crash reporting directories for external daemons.

Binary Validation & Spawning

Before launching a bundled agent binary, validate_agent_binary performs strict POSIX metadata verification:

  • No Symlinks: symlink_metadata(binary) asserts the path is not a symlink.
  • File Ownership: Asserts metadata.uid() == libc::geteuid() (must match the desktop runner).
  • Permissions: Asserts mode & 0o022 == 0 (prohibits group/world writable binaries) and checks execution bits (mode & 0o111 != 0).
  • Advisory Locks: Acquires exclusive flock on <socket>.desktop-agent.lock (mode 0o600) to prevent concurrent launcher race conditions.

Socket Takeover & Anti-TOCTOU Verification

If an existing socket is encountered but reports an incompatible protocol version, foks-desktop-app executes an audited takeover sequence (AgentTakeover):

// Step 1: Verify socket metadata and ownership let metadata = std::fs::symlink_metadata(socket)?; if metadata.file_type().is_socket() && (metadata.mode() & 0o077 != 0) { return Err(AgentError::new("unsafe-socket", "Socket permissions too open", false)); } // Step 2: Extract peer PID using kernel credentials let peer_pid = unix_peer_pid(&stream)?; // SO_PEERCRED on Linux / LOCAL_PEERPID on macOS // Step 3: TOCTOU device/inode check before prompt let current = std::fs::symlink_metadata(socket)?; if current.dev() != metadata.dev() || current.ino() != metadata.ino() { return Err(AgentError::new("agent-takeover-changed", "Socket inode changed", true)); } // Step 4: Re-check device/inode immediately before SIGTERM stop_incompatible_agent(socket, &target)?;

Takeover prompts the user via a native modal dialog displaying the target executable and PID. If the socket's inode or device changes while the modal is open, termination is aborted to prevent Time-of-Check to Time-of-Use (TOCTOU) exploits.

4. AppLock & Host-Delegated Authentication

FOKS delegates user authentication entirely to the host operating system. The application stores zero master passwords in memory or on disk, eliminating the threat of offline database dictionary attacks.

Platform Authentication Drivers

  • macOS (LocalAuthentication): Uses Apple's LAContext framework. It first probes LAPolicyDeviceOwnerAuthenticationWithBiometrics (Touch ID / Apple Watch). If biometrics are unconfigured or fail, it falls back to LAPolicyDeviceOwnerAuthentication (system account password). Prompts enforce a 60-second hardware timeout.
  • Linux (Polkit System Bus): Communicates with the PolicyKit daemon over the system D-Bus bus (org.freedesktop.PolicyKit1) requesting action org.foks.desktop.unlock. The installed policy file grants <allow_active>auth_self</allow_active>, allowing active desktop session users to authenticate with their own password without requiring root or sudo access.

Anti-PID-Reuse Protection on Linux

To prevent an attacker from terminating the FOKS desktop and rapidly spawning a malicious process with the same PID to inherit Polkit authorization, FOKS parses /proc/{pid}/stat field 20 (process start time in clock ticks). The start time is passed alongside the PID to Polkit's CheckAuthorization call, defeating PID recycling attacks.

The Generation Counter & Atomic Interval Binding

AppLock maintains an atomic counter: generation: AtomicU64. Every locking event increments this value. When sensitive mutations or multi-chunk file transfers occur, the operation captures an unlocked_generation token:

let access = crate::applock::unlocked_generation(app)?; // ... perform background preparation / fetch ... crate::applock::require_unlocked_generation(&app, access)?;

If the application locked and unlocked while a background task was running, the generation moved from $N$ to $N+1$. The post-check fails immediately with "app-locked", preventing data leakage across locking boundaries.

The Four-Step Lock Scrub

When lock_app() is triggered, the host executes four defensive purges in sequence:

  1. Catalog Purge: Wipes the cached catalog snapshot (*self.catalog.lock() = None) and advances the mutation epoch counter.
  2. Web Admin Window Termination: Iterates through all open auxiliary administration windows (web_admin::close_all) and forcibly closes them.
  3. Local Chat Concealment: Clears the active chat session generation token.
  4. Notification Center Purge: On macOS, invokes UNUserNotificationCenter to delete all delivered and pending push notifications, scrubbing message snippets from the macOS lock screen and notification shade.

5. Memory Hygiene & Zero-Knowledge Clipboard Management

Clipboard security is a major vulnerability in password management. Background clipboard logging tools and clipboard history extensions regularly archive plaintext credentials.

Digest-Only Fingerprinting

When a user copies a password or secret via copy_item_value, the secret is encapsulated in a Zeroizing<String> container. The string is written to the system pasteboard and dropped immediately:

pub fn copy_with_hygiene(app: &AppHandle, value: Zeroizing) -> Result<(), String> { let expected = PendingClipboard { digest: Sha256::digest(value.as_bytes()).into(), generation: NEXT_GENERATION.fetch_add(1, Ordering::Relaxed), }; // Plaintext value is dropped and zeroized here! *pending = Some(expected); // Auto-clearing thread spawned... }

FOKS retains only the 32-byte SHA-256 hash of the secret. If an attacker inspects process memory or analyzes a core dump, no plaintext credential remains.

Timed Auto-Clearing with Non-Destructive Race Avoidance

  • Linux Timeout: 15 seconds.
  • macOS Timeout: 30 seconds. Linux enforces a shorter window because Linux desktop environments lack a standardized clipboard concealment protocol.
  • macOS Concealed Marker: On macOS, FOKS tags the pasteboard item with org.nspasteboard.ConcealedType, instructing utilities like Raycast, Alfred, and 1Password not to log the entry.

Non-Destructive Race Check

When the clearing timer expires, FOKS hashes the current clipboard text. If the hash does not match expected.digest (because the user copied another string in the interim), the clipboard is left untouched. FOKS never clobbers unrelated user data.

6. Native File Streaming & Drag-and-Drop Isolation

In standard web applications, file uploads load entire files into JavaScript ArrayBuffer or Blob objects. In FOKS, secret file bytes never touch the webview memory space.

Drag-and-Drop Path Authorization

When a file is dragged onto the window, Tauri intercepts WindowEvent::DragDrop:

  1. Rust checks the dropped paths. If exactly one UTF-8 path is dropped, it is stored in pending_upload_paths.
  2. Rust emits foks://drop-paths with the path string to allow the UI to display the file name and size.
  3. When the user clicks "Save", the webview sends create_file_item(store_id, path, source_path).
  4. Rust validates that source_path exists in pending_upload_paths. An unrecorded path (e.g. attempting to point to /etc/shadow) fails immediately with drop-not-authorized.

Thresholds & Frame Streaming

  • MAXIMUM_INLINE_KV_BYTES = 128 KB: Payloads smaller than 128 KB are transmitted inline.
  • MAXIMUM_KV_PAYLOAD_BYTES = 700 KB: Payloads larger than 128 KB stream via put_kv_stream in 700 KB frames. Chunk buffers use Zeroizing<Vec<u8>> and are wiped immediately after socket transmission.
  • MAXIMUM_DOWNLOAD_BYTES = 512 MB: Hard ceiling on vault file downloads.

7. Hardware Cryptographic Tokens (YubiKey PIV)

FOKS natively interfaces with YubiKey hardware tokens over PC/SC smartcard protocols (using PCSC.framework on macOS and libpcsclite / pcscd on Linux).

Dedicated Retired PIV Slots & Dual-Slot Cryptography

Rather than using standard PIV authentication slots (which may conflict with corporate smartcard certificates), FOKS allocates keys from NIST SP 800-73-4 retired key slots (0x82 through 0x95):

PIV Slot Type Cryptographic Algorithm Role & Purpose
Signing Slot ECC P-256 (secp256r1) Generates hardware-bound ECDSA signatures for account authentication and vault operations.
PQ Seed Slot ECC P-256 (Derived Key ID) Compressed public key derives YubiPQKeyID used for Post-Quantum ML-KEM key encapsulation.

Self-Revocation Protection

In require_software_revocation_signer, FOKS enforces a strict security invariant: a hardware token cannot sign its own revocation certificate. Revoking a lost or retired YubiKey requires signing the revocation using a valid software device key (dev-*).

Safe PIN Retry Configuration

Executing the standard PIV SET PIN RETRIES command inherently resets the token PIN to 123456 and PUK to 12345678. To prevent tokens from being left in a factory-default state if an error or disconnection occurs mid-operation, FOKS enforces atomic preflight: retry configurations are accepted only on empty, unenrolled tokens, and custom PINs/PUKs are restored atomically before any cryptographic keys are generated.

8. The Desktop UI Shell & Grid Layout

The desktop UI is styled in apps/desktop/src/styles/shell.css and apps/desktop/kit/tokens.css. Custom layout properties are anchored directly on the .app container to eliminate layout thrashing:

.app { --topbar-h: 48px; --side-w-open: 200px; --side-w: var(--side-w-open); --side-track: auto; --details-w: 300px; display: grid; grid-template-columns: var(--side-track) minmax(0, 1fr); }

The Six-Tab Navigation Rail

The navigation rail (nav.side.rail) organizes the user experience into six primary destinations:

  1. Files: Flat and hierarchical vault items, small-file previews, and link pointers.
  2. Chat: Cross-team channel inbox and conversation view.
  3. Teams: Groups, shares, federation rosters, and member administration.
  4. Devices: Hardware keys, paired computers, and paper recovery keys.
  5. Settings: Preferences, server connection parameters, and security policies.
  6. Accounts: Acting account profile switcher, attention items, and server groupings.

The rail collapses into an icon-only track of 56px (.is-narrow). Width preferences persist in localStorage under sideCollapsed. Unread badges use the high-visibility token --unread: #ff6f21.

Blocking States and Veils

When the client is not in a normal operating state, non-intrusive veils take over:

  • Starting: Rail and topbar remain visible but dimmed; content area renders Starting the FOKS agent….
  • Stopped (restart-required / recovery-required): Centered card displays actionable copyable CLI repair commands (e.g. foks-rs state recover).
  • Locked: Full-window takeover covering rail and topbar with a 6px backdrop blur, hiding account names and unread counts.

9. Navigation State Machine & Guard Architecture

Deep Links & The Location Codec

All navigation states are represented by the TypeScript discriminated union Location and encoded into URL search parameters (?state=<kind>&store=<StoreRef>). The desktop synchronizes state via window.history.replaceState, enabling instant reload restoration while disabling browser history stack pollution and native webview swipe gestures.

Trackpad Gesture Physics (Swipe-Back)

Horizontal swipe navigation is handled by a custom physics engine in SwipeBackTracker:

  • Arming Threshold: BACK_DISTANCE_PX = 120px of horizontal travel required to trigger navigation.
  • Idle Debounce Window: GESTURE_GAP_MS = 120ms. Navigation commits only after wheel events cease for 120ms.
  • Momentum Absorption: Reversing direction before the finger leaves the trackpad decays progress back to zero, allowing cancellation.
  • Exclusion Filters: Gestures are suppressed if vertical scroll dominates ($|\Delta X| \le 2|\Delta Y|$), if modifier keys are pressed, or if an open modal dialog owns the window.

The Navigation Guard Engine

Form screens register guards via useNavigationGuard to prevent data loss. A guard evaluates an intent and returns one of three verdicts:

Verdict Behavior & Effect Typical Usage
null Navigation proceeds unimpeded. Unchanged views or read-only pages.
prompt Displays an alert dialog (NavigationPrompt) with Discard / Cancel options. Unsaved password drafts or pending invitations.
refuse Hard halt. Emits a warning toast and aborts navigation immediately. Active cryptographic writes or key enrollment in progress.

Refusal Precedence

Guards are evaluated in registration order. Any guard returning refuse immediately aborts the entire pipeline. A confirmed prompt dialog can never bypass a subsequent guard's refusal.

10. State Coordination, Caching & Inactivity Concealment

Snapshot Serialization (CatalogCoordinator)

To prevent UI tearing during rapid mutations, CatalogCoordinator serializes catalog snapshots. Concurrent read requests coalesce into a single in-flight promise. If mutations occur during a fetch, the coordinator marks dirty = true and immediately schedules a single trailing refresh.

In-Memory Metadata Repository & Freshness

Device and group metadata is cached in-memory via MetadataRepository with a 60-second freshness window (freshFor = 60_000ms). Switching tabs results in zero-latency rendering from memory. When a mutation occurs, repository.invalidate(['account-devices', profile, store]) advances the cache generation token, rendering stale data without flicker while a background fetch refreshes the view.

Window Inactivity Concealment (useConcealOnInactive)

When the window loses focus or becomes hidden (visibilitychange), sensitive UI elements are masked:

  • Vault passwords and revealed recovery codes mask immediately.
  • Pairing offers and QR codes hide until focus returns.
  • If an asynchronous secret arrives after blur, useLayoutEffect masks it before paint.

11. First-Run Onboarding, Receipts & Pairing Ceremonies

The Setup Routes

  • Invited Journey (path='invited' • 4 Steps): Connect Server → Create Account → Backup Key → Discover & Join Team.
  • Own Journey (path='own' • 3 Steps): Connect/Launch Server → Account Creation/Recovery → Protection.

Account Operation Receipts (account-operation-receipts-v1)

To eliminate ghost accounts or replay attacks during network dropouts, account creation mutations record atomic on-disk receipts:

{ "version": 2, "state_id": "sha256-state-identity...", "attempt": { "host_id": "02...", "account_alias": "alice" }, "outcome": "Unknown" // Initialized before network dispatch }

Before sending the mutation to the server, the outcome is recorded as Outcome::Unknown and synced to disk (including a parent directory sync). If the agent crashes mid-mutation, the operation cannot be blindly re-dispatched without explicit resumption checks.

Pairing Phrases vs. Paper Backup Keys

Mechanism Token Composition Entropy & Lifespan
Device Pairing (KEX) 13 tokens: 7 BIP-39 words alternating with 6 decimal numbers (0–255). 125-bit ephemeral secret. Used for peer-to-peer computer pairing.
Paper Backup Key 17 tokens: 9 BIP-39 words alternating with 8 decimal numbers (up to 8,192). 203-bit long-term master root seed. Zero state written until confirmed.

12. StoreRef Hierarchy & Team Federation

The Identity Triad & Anti-Spoofing Deep Links

FOKS differentiates between three identity concepts:

  1. alias: A local display label (e.g. work). Ambiguous across servers.
  2. profile: The server connection configuration.
  3. StoreRef: A canonical, globally unambiguous JSON string encoding the profile, alias, and unique team ID.

Alias Collision Defense

Deep links strictly require ?store=<StoreRef>. Legacy parameters such as ?account=personal are explicitly rejected and stripped. If an attacker could trigger actions via ?account=personal, a malicious link could trick a user into executing corporate operations against a personal vault.

Team Rosters & Visibility Bands

Team members are categorized as People, Machines, or Remote Groups. The internal visibility band (Member (0)) is hidden from general UI views, appearing only when permissions diverge (e.g. restricted channels or non-zero visibility tiers).

When remote federated teams are admitted, FOKS tracks admission status. Discrepancies render as diagnostic chips:

  • No admission record: Team is in the cryptographic roster, but local admission is missing.
  • Ambiguous admission: Multiple local admission records match a single roster entry.

13. Realtime Chat Subsystem & Resilient Operations

The Chat tab provides cross-team conversation aggregation via TeamInbox. When chat is opened without parameters, it automatically opens the conversation with the most recent message across all reachable teams.

Durable Submission IDs

Channel creation generates a durable UUID submission token. If network connectivity drops during creation, the submission enters state: 'unresolved'. The UI re-polls the agent's pending ledger rather than creating duplicate channels.

Validation Parity with Rust Backend

Constraint Specification Limit Validation Rule

14. Systems Limits & Open Risks

A secure system is defined as much by what it refuses to do as by what it implements.

Deliberate Desktop Omissions

  • No Global Directory Search: To prevent enumeration and metadata harvesting, FOKS provides no server user directory. Members must be invited by exact handle.
  • No Inline Role Elevation: Members cannot be upgraded to Admin/Owner inline; role changes require explicit group administrative workflows.
  • No Message Reactions or Deletion: Messages are immutable. Deletions and reactions are omitted until a cryptographic compaction standard is finalized.
  • No Cross-Team Content Search: The search bar filters team names and channel labels, but does not execute full-text search across encrypted message history.

Documented Architectural Risks (from ISSUES.md)

Known System Boundaries

  • Chat Server Retention (High Priority): Server-side message storage allows up to 1 MiB per message envelope with no current compaction or pruning path. A malicious member could flood messages to exhaust server SQLite disk space.
  • Client Terminal Operation Bloat (Medium Priority): Confirmed and rejected chat operations remain permanently in client SQLite tables (chat_operations), accumulating indefinitely without tombstones.
  • Server Invitation Limits (Medium Priority): The server enforces hard lifetime limits (65,536 remote requests, 1,000,000 local requests). Exceeding these limits permanently blocks new invitations.
  • Realtime Member Fanout Cap (Lower Priority): Realtime delivery mutates after scanning at most 1,024 direct membership rows. Teams exceeding 1,024 members fail to deliver realtime notifications.
