A · Delivery states

Every row keeps the avatar and author of a sent message, and a line under the text says what happened and offers only the actions that state allows. Messages written in this session show their time; operations restored from an earlier session (the Couldn't post and Cancelled rows) do not, because ChatOperation carries no time. Today the same work appears in three layouts: OutgoingRow, a bare PendingRow article without avatar or author (chat-thread.tsx:385), and the Needs attention section. A rejection reads as a reason instead of "The server rejected this operation (12006)". The rows are a gallery: in real use a Sending row and a no-connection row would not appear together.

Findings

  • chat-ux-delivery-statesShips on today's data
    One MessageRow with a delivery slot for sent messages, outgoing messages and tracked operations, with a fixed vocabulary: Sending, Queued, Not sent, Checking delivery, Couldn't confirm delivery, Couldn't post, Cancelled, Waiting for access. Copy comes from a table keyed on the rejection code and CommandError.code; the agent's message text goes to diagnostics, never to the row.
  • chat-code-pending-row-actionsShips on today's data
    Retry, Check again, Edit and Discard come from service-owned action availability (retryOperation, checkOperation, cancelOperation and a rows() view model), so no component picks attempt or reconcile itself (pending-row.tsx:105).
  • chat-code-outgoing-state-machineShips on today's data
    Rows read one derived phase from a transition() function. Each drive carries an attempt token, so a status reply from an earlier failed attempt cannot overwrite the phase of a Retry that started after it (send-service.ts:1072).

Findings

  • chat-ux-sender-identityNeeds agent/IPC
    History gains senders: [{uid, username?, member}]. member comes from the team chain the chat session already verifies; the desktop validates at most one entry per page row and usernames within CHAT_LABEL_BYTES.
  • chat-ux-sender-identityNeeds client library
    Usernames need a per-sender user-chain load with the team view token, which this server still authorizes for removed members (to be confirmed against Go v0.1.9), cached in a bounded LRU in the agent. A failed load yields no username, not an error.

The Unknown member fallback itself is desktop code, but without the senders list every former member would also read as Unknown member, so it is shown here with the agent work.

Findings

  • chat-backend-single-message-poisons-channelNeeds client library
    Per-message ChatContent::Unverifiable verdicts for decryption failure, non-UTF-8 text, an unsupported sender or attribution, and a missing key generation.   • chat-backend-single-message-poisons-channelNeeds agent/IPC
    An unverifiable content kind in agent-proto ChatContent, validated in chat-contract.ts. No wire change. Go v0.1.9's own client also fails a whole fetch on such a row, so this helps FOKS-RS clients only.
