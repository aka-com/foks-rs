A · Replies

Today the client never decrypts Edit, Reaction or Reply bodies (history.rs:298), so each row reads "This message type is not supported yet." Because the newest row is unsupported, prepare.rs:221 refuses every send with "latest message has unsupported content", and Retry fails the same way.

No conforming client writes these rows today: Go v0.1.9 sends only Basic bodies, and the Rust server rejects any other kind (messages.rs:16). The pegged, unsupported and undecryptable rows here are what a nonconforming member client can store on a Go v0.1.9 host, which keeps any message kind.

Proposed, the client opens pegged bodies with the existing nonce, which authenticates their metadata, and the desktop draws a reply with its quoted parent. Edits and reactions become read-only markers on their target, unsupported and unverifiable rows become one-line placeholders, and a new message chains to the latest observed row, so no single row closes the channel.

Sending a reply is gated separately. The Reply action and the "Replying to" bar appear only when the host offers replies, because a Go v0.1.9 reader fails a whole history page on any non-Basic body.

Findings

  • protocol-chat-pegged-reply-bodiesNeeds client libraryNeeds agent/IPC
    Read side: RealtimeKeys::open_message checks noncer.metadata.kind against the body kind, with no wire or server change. The agent then has to pass a reply kind with its parent ID; chat-contract.ts carries only text, unsupported and oversized today.
  • protocol-chat-pegged-reply-bodiesNeeds protocol/serverDeferred
    Send side: lift the Rust server's Basic-only rule (messages.rs:16) and negotiate so a channel with Go v0.1.9 readers never receives a reply. This belongs to the deferred extended-chat work.
  • chat-backend-single-message-poisons-channelNeeds client libraryNeeds agent/IPC
    Per-message verdicts: the 9:41 AM row is Unverifiable instead of failing the page, the reply to it reads "Original message unavailable", and prepare_fresh_send chains past both. The agent needs an unverifiable content kind.

B · Attachments

A file goes into the Engineering vault at /.chat/<channel-id>/<operation-id>, and the message itself is Basic text with a foks-kv: reference, the size, the media type and the SHA-256. FOKS draws a card and checks the hash after fetching; Go clients see the text line and can fetch the file with KV tools.

The agent journals the upload and the send as one operation, so the row reads Uploading…, then Uploaded, sending…, and a failed upload keeps the file for Retry. Before the first file, an owner creates /.chat once, because the vault root is owner-write: satoshi gets a Set up button, vitalik gets a notice naming the owner. Each channel's folder, /.chat/<channel-id>, is then made by the channel's creator with the channel's read and write roles; the mockup assumes #deploys already has one.

Phase 1 does not use the chat capability, so on a basic-only host files still work and the Host control changes only the explanation in the attach menu. Details says that any member who can post can replace or remove a file, which Phase 1 cannot prevent.

Findings

  • chat-backend-attachments-via-team-kvNeeds agent/IPC
    One journaled workflow: KV put, then a Basic send. The KV path derives from the chat operation ID, so recovery is idempotent. The channel column preview ("priya.n sent a file: …") comes from the agent's parse of the reference line.
  • chat-backend-attachments-via-team-kvNeeds client library
    Clients compare /.chat/<channel-id> roles with the verified channel metadata before uploading or rendering, then check the SHA-256 after fetching ("Hash mismatch — file not shown", "File no longer available").
  • chat-backend-attachments-via-team-kvNeeds agent/IPC
    Owner setup: the team vault root is written by owners only (team.rs:1347) and the server checks the parent's write role (kv.rs:920), so members cannot create /.chat.
  • chat-backend-attachments-via-team-kvNeeds native shell
    Download, Choose a file… and drop can reuse the Files commands (download_file, pick_import_file, import_dropped_file in src-tauri/src/commands/vault.rs). Open, on a card or a thumbnail, needs a new command: the desktop has no way to hand a decrypted file to another app today.
  • chat-backend-attachments-via-team-kvDeferred
    Phase 2: RtChatPurpose::Attachment in format 2 for server-enforced authorization and retention.

C · Channel settings

Channel info gains Edit channel for admins and owners; this tab opens on the form, and Cancel shows the panel with the button. The name check follows channelNameProblem in presentation.ts: 3–32 characters, no spaces or double hyphens, "general" is the team's general channel, and names are unique in the team. Both fields lowercase as you type, as in the Create channel sheet, because the client library stores names and descriptions lowercased. Read access is shown but fixed, because history.rs:307 requires every message box to use the channel's current read role.

Save calls foksChatUpdateChannel with expected_sequence, journaled: the panel says Saving… until Acme confirms. If another device changed the channel first, the form stops with "Channel changed on another device" and a side-by-side review.

Archive asks for confirmation, then the composer gives way to a read-only band and the channel moves to an Archived group in the column. Go clients see a channel only owners can post in, not a read-only one; the dialog says so.

Findings

  • chat-backend-channel-management-format1Needs protocol/server
    foksChatUpdateChannel {channel, expected_sequence, set_version, name?, description?, write_role?, archived?} behind a channel_update feature, once a durable method namespace exists. The server keeps id, tier, format and roles.read fixed and writes sequence + 1.
  • chat-backend-channel-management-format1Needs client library
    A chat_channel_revisions table rejects a lower sequence, and uncertain-create reconcile compares immutable fields only (recovery.rs:24). A new ChatOperationKind extends the check at schema.rs:83.
  • chat-backend-channel-management-format1Needs agent/IPC
    PrepareChannelUpdate, reusing Status, Attempt and Reconcile, drives Saving…, Saved and the conflict review.
  • chat-backend-channel-management-format1Deferred
    Delete stays disabled until a retention floor exists. Read-role changes stay format 2 only. Go v0.1.9 tolerance of sequence > 1 still needs oracle cases.

Data

The finding proposes admin or owner for admin-tier channels and leaves the rule for member-tier channels such as #random open; the mockup assumes admin or owner everywhere, so satoshi (owner) and vitalik (admin) see the same panel. #random has no description in Kit.data.

  • Start an edit, then use Edit this channel on Travel Mac, then Save.
  • Turn on Archive channel, confirm, and open the Archived group in the column.
  • Right-click a channel, or focus it and press Shift+F10, for Edit channel.

D · Presence

The typing line sits above the composer of the focused channel: "priya.n is typing…" or "priya.n and 2 others are typing…". A small avatar stack sits under the last message each member has read; hovering names them, and clicking lists them with a link to the privacy setting.

Read positions come only from members who turned on "Share when I have read messages" in Settings › Preferences, which is off by default. Typing lives in an in-memory hub with a TTL of about 6 seconds and is never stored. On a basic-only host there is no typing line and no stack, and the setting is disabled with the reason.

Findings

  • chat-backend-presence-typing-receiptsNeeds protocol/server
    Rust-only foksChatReadStates, foksChatTyping and foksChatPresencePoll, behind a presence feature; share_read_state in rt_user_inboxes, off by default. Today rt_read_through wakes only the reader (inbox.rs:396).
  • chat-backend-presence-typing-receiptsNeeds agent/IPC
    The agent long-polls foksChatPresencePoll for the focused channel only, under the existing poll permit limit, and forwards typing and read-state changes.

Data

Read positions are mockup data. priya.n and lee have read through satoshi's 9:58 AM message (added to Kit.data), vitalik through lee's message, and sam.ortiz through vitalik's. You never appear in your own stacks.

  • Change Typing above the window.
  • Hover a stack, then click it and follow Change in Settings. Turn the setting on, then go back to Chat.

E · Basic chat only

Settings › Account › Acme gains a Chat section that says what the host offers and what that means in a channel. Opening this tab sets Host to Basic chat only; switch it to compare. Leaving the tab puts Host back unless you changed it here.

On a basic-only host nothing errors. Replies still render, because reading them needs no host support; Reply, Edit channel and the read-receipt setting are disabled with the reason; typing and read stacks are absent; files still work through the team vault.

The proposed response is [1, host, features]. The client ignores feature IDs it does not know (Acme lists one here). Technical details shows the two fallback rules the finding offers, which are not settled: a server answers a newer request with the version it knows, or a client that gets BadArguments asks again with version 1.

Findings

  • protocol-chat-capabilities-extensible-shapeNeeds protocol/serverNeeds client library
    Replace the fixed eight-field array (realtime_extension.rs:79) with a feature-ID list. Unknown IDs are ignored, dependencies are checked only among known IDs, and a higher version maps to basic only with a logged diagnostic instead of an error.
  • chat-backend-capability-negotiation-not-forward-compatibleNeeds protocol/server
    Settle the fallback rule and the durable vendor method namespace (ISSUES.md) together. No format-1 bit for pegged content, because Go v0.1.9 clients cannot read it.
  • chat-backend-capability-negotiation-not-forward-compatibleNeeds agent/IPC
    ChatAction::Capabilities, cached per CheckedProfileSession and dropped on identity change. chat.rs:9 has no such action today.
