### r2-compat-long-poll-closes-on-concurrent-go-call

**Long-poll routes close the connection when a Go client multiplexes a second call, breaking Go KEX provisioning via a Rust host**

Priority: high · Type: compatibility · Origin: pre-existing · Effort: L · Layers: server, protocol

LongPoll::run (crates/foks-server/src/net/session.rs) awaits the handler against stream readability and returns None when the peer becomes readable; serve() then leaves the connection loop and the connection closes unanswered. The comment justifies this with 'Snowpack is request/response serial', which is false for the protocol library: go-snowpack-rpc multiplexes calls by seqid over one transport and its receiver serves each inbound call in its own goroutine. The Go v0.1.9 agent's KEX engine uses the session's cached RegGCli for Send and Receive, and in KexProvisioner.receiveHello and KexProvisionee.receiveLink the device whose user types the pairing code issues a fail-fast Receive (and, for the provisionee, Send then Receive) while a waitForIt Receive with PollWait of one hour is pending on the same connection. The Rust server honours that hour (MAX_BLOCKING_WAIT = 1 h in net/session/kex.rs), so the second frame always lands mid-poll: the server closes the connection, both Go calls fail with RPC EOF, and provisioning fails deterministically. The Rust client polls KexReceive serially in bounded slices and is unaffected. Only the KEX route is confirmed to receive concurrent Go calls; the OIDC completion poll and RtPollInbox share the same close-on-readable code but no concurrent Go caller was verified for them. Go compat coverage does not exercise this (liveKexRelay sends then receives serially; no Go-agent provisioning run exists), and crates/foks-server/README.md:99 says interactive software-device KEX is supported without qualification. Present at d3ee213; commit 100bc47 consolidated the three long-poll branches into one helper and restated the serial assumption as a rule.

Evidence:

- [`crates/foks-server/src/net/session.rs:642`](../../crates/foks-server/src/net/session.rs#L642): `_ = peer_readable => return Ok(None)` under the comment 'Snowpack is request/response serial...'
- [`crates/foks-server/src/net/session.rs:485`](../../crates/foks-server/src/net/session.rs#L485): `let Some(outcome) = outcome else { break; }` closes the connection unanswered
- [`crates/foks-server/src/net/session.rs:355`](../../crates/foks-server/src/net/session.rs#L355): KexReceive routed through poll.run(stream.get_ref().0.readable(), ...)
- [`crates/foks-server/src/net/session/kex.rs:19`](../../crates/foks-server/src/net/session/kex.rs#L19): MAX_BLOCKING_WAIT = 1 h; receive() honours min(requested, MAX), so the Go waitForIt Receive is pending for the whole pairing window
- `github.com/foks-proj/go-foks@v0.1.9/client/libclient/kex.go:456` (Go module source): receiveHello runs getSessionFromUI (fail-fast Receive at 370) concurrently with receiveHelloOurChannel (PollWait 1000*60*60 at 309); receiveLink (927) does the same with Receive/Send/Receive at 866-895
- `github.com/foks-proj/go-foks@v0.1.9/client/agent/session.go:226` (Go module source): SessionBase.RegGCli caches one *core.RpcClient per session; connectionMgr.getXp returns the cached transport while connected
- `github.com/foks-proj/go-snowpack-rpc@v0.0.2/rpc/receiver.go:130` (Go module source): handleReceiveDispatch serves each inbound call in its own goroutine; call.go:54 multiplexes by seqid
- [`tools/foks-v019-oracle/go_client_rust_live_test.go:167`](../../tools/foks-v019-oracle/go_client_rust_live_test.go#L167): liveKexRelay is Send then Receive serially; run-go-client-compat.sh and the go-driver scripts have no Go-agent provisioning run
- [`crates/foks-server/README.md:99`](../../crates/foks-server/README.md#L99): 'Interactive software-device KEX is supported' with no Go-client qualification

Recommendation: Stop treating readability as cancellation. When the socket becomes readable during a long poll, read the next frame (noting readiness is observed on the raw TcpStream under rustls, so a frame already buffered inside rustls must also be drained): a zero-byte read or I/O error is a shutdown; a complete call frame is a pipelined request and must be served, either concurrently with responses in completion order (Snowpack responses carry seqnos) or queued until the poll resolves, with a per-connection cap on queued frames to keep the memory and permit bounds. Add an oracle test that issues a fail-fast Kex.receive on the same core.RpcClient while a waitForIt Kex.receive is pending, and a Go-agent two-device provisioning run to run-go-client-compat.sh. Until then, qualify crates/foks-server/README.md:99 and book/17-wire.qmd: Go device provisioning through a Rust host is not supported.

Verifier note: Two verifiers confirmed every claim against HEAD and the vendored Go sources and kept high: the repository treats Go v0.1.9 compatibility as a hard requirement, the failure is deterministic rather than a race, and nothing tests or documents it. Corrections applied: exact line numbers (642, 485, 355); only the KEX route is a confirmed concurrent-Go-call case; the Rust client is unaffected; the fatal path is the waitForIt goroutine returning RPCEOFError. Not a duplicate: STATUS.md:879's per-source long-poll cap concerns admission limits.

### r2-compat-rate-limit-refusal-sequence-zero

**Per-source request-rate refusal answers at sequence 0, so Go and Rust clients on a reused connection get an unmatched response and EOF instead of the documented status 1012**

Priority: medium · Type: compatibility · Origin: pre-existing · Effort: S · Layers: server, docs

When the per-source request token bucket is empty, serve() (net/session.rs:273-285) reads only the frame length, writes encode_status_response_at(&RpcStatus::RateLimited, 0) and returns, closing the connection. Both go-snowpack-rpc (call.go:55-61) and the Rust PooledConnection (foks-client transport.rs:292-336) start seqids at 0 per connection and increment, so only the first call on a connection carries sequence 0. For any later call the Go transport treats the response as CallNotFoundError (swallowed by shouldContinue) and the pending call fails with RPC EOF when the connection closes; the Rust client raises Error::Sequence { expected, received: 0 } (client_response.rs:88-93) and leaves the connection unreusable. The handler-cap and poll-permit refusals a few lines later already use the decoded sequence. A fresh connection from an exhausted source is usually refused earlier by the connection bucket, so the request-bucket refusal lands mostly on reused connections, where the mismatch is the common case. crates/foks-server/README.md:306-308 and book/18-server-storage.qmd:255-256 state unconditionally that such a request 'receives FOKS status 1012'. Neither client retries on either outcome, so the practical effect is that a throttle surfaces as a generic sequence/EOF error (bypassing the agent's RateLimited mapping at main.rs:2318) and that Go clients may treat it as a connection failure and reconnect against a source being throttled. STATUS.md:189 already records 'the per-IP limiter refuses at sequence 0 before it reads the call body' (misnaming the code as 1059) as a reason not to classify 1012 as a definite rejection, but records no fix; correcting the sequence removes that obstacle. The request bucket does not exempt loopback, so a testkit reproduction is possible from loopback with a small request_burst.

Evidence:

- [`crates/foks-server/src/net/session.rs:280`](../../crates/foks-server/src/net/session.rs#L280): `encode_status_response_at(&RpcStatus::RateLimited, 0)` after reading only the frame length, then return (close)
- [`crates/foks-server/src/net/session.rs:465`](../../crates/foks-server/src/net/session.rs#L465): handler-cap refusal uses the decoded `sequence`
- `github.com/foks-proj/go-snowpack-rpc@v0.0.2/rpc/call.go:55` (Go module source): nextSeqid starts at 0 per connection; message.go:206-210 turns an unknown seqno into CallNotFoundError; transport.go:216 continues
- [`crates/foks-rpc/src/client_response.rs:88`](../../crates/foks-rpc/src/client_response.rs#L88): Rust client returns Error::Sequence on mismatch instead of RemoteStatus 1012
- [`crates/foks-server/README.md:308`](../../crates/foks-server/README.md#L308): 'a framed request that exceeds its bucket receives FOKS status 1012 and the connection closes'
- [`book/18-server-storage.qmd:256`](../../book/18-server-storage.qmd#L256): same unconditional claim
- [`docs/review/STATUS.md:189`](../../docs/review/STATUS.md#L189): records the sequence-0 refusal only as a reason not to treat the status as a definite rejection; misnames the code as 1059

Recommendation: Read the bounded call body (already limited by maximum_frame_bytes and the request memory semaphore) far enough to decode the seqno before answering, and send 1012 at that sequence as the handler-cap path does; alternatively close without a response and change the README, book and STATUS.md:189 to say so. Add a testkit case with a small request_burst that makes two calls on one loopback connection and asserts the second refusal decodes as status 1012 in the Rust client (and in the Go oracle client).

Verifier note: Both verifiers confirmed the mechanics and the pre-existing origin (8cb0d1a). One lowered to low because neither client retries on either outcome so only the error class and two doc sentences differ; the other kept medium because the refusal becomes an ambiguous outcome for mutations and blocks treating 1012 as a definite rejection (STATUS.md:189). The synthesis keeps medium given the documented contract does not hold and the fix is S. Not a duplicate: STATUS.md:189 does not track the consequence or a fix.
