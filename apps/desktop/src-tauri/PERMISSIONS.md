# FOKS desktop: the resolved permission posture

Audited against `gen/schemas/acl-manifests.json` and `gen/schemas/capabilities.json`
generated by `tauri-build`. Verify these files upon updating `tauri` dependencies
to ensure documentation accurately reflects schema permissions.

## What the capability grants

`capabilities/default.json` is the only capability. It scopes to the single
window `main`, has no `remote` entry, and lists three core entries, each naming
one command:

```
core:event:allow-listen
core:event:allow-unlisten
core:window:allow-start-dragging
```

followed by one `allow-<command>` entry for each FOKS command (see
[FOKS commands](#foks-commands)).

The three core permissions resolve to exactly three invocable Tauri commands,
verified by `the_resolved_capability_reaches_only_main_and_the_registered_commands`
in `src/lib.rs`:

```
core:event|listen
core:event|unlisten
core:window|start_dragging
```

| Permission | Why the renderer needs it |
| --- | --- |
| `core:event:allow-listen` | `dragdrop.rs` emits `foks://drop-hover` and `foks://drop-paths` **from Rust** to the `main` window. `src/bridge.ts` subscribes with `listen` from `@tauri-apps/api/event`; without this the drop zone has no hover state and a drop reports nothing. |
| `core:event:allow-unlisten` | The other half of the same subscription: `listen` resolves to an unlisten function, and `bridge.ts` calls it on unmount. Granting listen without unlisten leaks a handler per mount. |
| `core:window:allow-start-dragging` | The command Tauri's own injected `data-tauri-drag-region` script calls to move the window under an overlay title bar (`titleBarStyle: "Overlay"`, `hiddenTitle: true`). It moves this app's own window and can do nothing else. The frontend does not mark a drag region today; the grant is kept because the window is configured for one, and it is pinned by an exact-set test rather than assumed. |

`emit` and `emit_to` are omitted from webview permissions. Drag-drop events
are emitted unidirectionally from Rust to the window, preventing renderer scripts
from synthesizing unauthorized drop events.

## What the capability does **not** grant

The `core:default` permission set was removed because it expanded to nine
sub-defaults and 92 individual commands. Key omitted permissions include:

| Was reachable through | Commands dropped |
| --- | --- |
| `core:image:default` | `from_path` **read any file the webview named**, bounded by nothing in the ACL, in an application whose whole design keeps file bytes out of the renderer. Also `new`, `from_bytes`, `rgba`, `size`. |
| `core:webview:default` | `internal_toggle_devtools` — an inspector over a window that renders secrets — plus `get_all_webviews`, `webview_position`, `webview_size`. |
| `core:path:default` | Eight path *string* commands (`resolve`, `resolve_directory`, `normalize`, `join`, `dirname`, `extname`, `basename`, `is_absolute`). No filesystem access — that lives in `tauri-plugin-fs`, which is not a dependency — but FOKS composes no paths in the renderer either. |
| `core:menu:default` | 22 menu-construction commands. FOKS builds no menu from JS. |
| `core:tray:default` | 12 tray commands. |
| `core:app:default` | `version`, `name`, `tauri_version`, `identifier`, `bundle_type`, and the listener registry. FOKS answers all of this through its own `app_info` command. |
| `core:window:default` | 28 read-only window queries plus `internal_toggle_maximize`, the double-click-titlebar behavior. If double-click-to-maximize is ever wanted, add `core:window:allow-internal-toggle-maximize` deliberately — see below — rather than restoring the set. |
| `core:resources:default` | `close` on resource-table handles. |
| `core:event:default` | `emit` and `emit_to`, alongside the listen/unlisten that were kept. |

Key architectural considerations regarding command permissions:

- **Whether a command is compiled in is not the security boundary.** The tray
  commands are `#[cfg(all(desktop, feature = "tray-icon"))]`
  (`tauri-2.11.5/src/lib.rs:112`) and this crate does not enable `tray-icon`,
  so they are not registered in a Cargo build of this package. That is a
  property of *this crate's feature set*, and Cargo unifies features across a
  workspace: a sibling in the same build that requires `tray-icon` can make them
  present again without touching this file. The same holds for
  `internal_toggle_devtools`, which is
  `#[cfg(all(desktop, any(debug_assertions, feature = "devtools")))]`
  (`tauri-2.11.5/src/webview/plugin.rs:180,253`) and is therefore compiled into
  every debug build. Feature unification decides what exists; the capability
  decides what the webview may call. Only the second is a control, and it is
  the one asserted by test.
- **Capability ACL enforcement.** Ungranted permissions are blocked by the Tauri
  ACL regardless of whether the underlying plugin commands are compiled into the binary.

Also absent, and for the same reason:

- **No notification permissions.** The webview cannot show a notification
  itself: FOKS links neither `tauri-plugin-notification` nor `notify-rust`, and
  the capability grants no notification API. Desktop alerts are raised by
  native code behind the `chat_local` command, which checks the main window,
  the unlocked generation and the stored alert settings first, through
  `UNUserNotificationCenter` on macOS and the `org.freedesktop.Notifications`
  service on the session bus (`zbus`) on Linux. `set_unread_badge` draws the
  app icon's unread count behind the same main-window check and is refused
  while the app is locked.
- **No plugin permissions at all.** `tauri-plugin-dialog` and
  `tauri-plugin-clipboard-manager` are registered in `run()` and their webview
  APIs are unreachable: `dialog:default` (`allow-message`, `allow-save`,
  `allow-open`) and `clipboard-manager`'s permissions are absent, so
  `invoke('plugin:dialog|open')` and `invoke('plugin:clipboard-manager|read_text')`
  are refused. Both plugins are driven **from Rust** — the save-destination
  picker, the import/replace picker, and the copy-with-clear — which is the
  point: the webview asks for the operation, but never receives a native-picked
  source path or file contents. `tauri-plugin-single-instance` has no webview
  API at all.
- **No filesystem, shell, http or fs-scope permissions.** Those plugins are not
  dependencies.

## FOKS commands

The commands registered with `generate_handler!` in `lib.rs` are the rest of
the IPC surface. Tauri checks a capability before running one of them only
when the app declares an ACL manifest; without one, a window on a local origin
can call every registered command. `build.rs` therefore declares the manifest:
it passes every command name to `tauri_build::AppManifest::commands`, which
writes an `allow-<command>` and a `deny-<command>` permission per command into
`permissions/autogenerated` (generated, not tracked). `capabilities/default.json`
grants each `allow-<command>` to the `main` window. No capability names a
`host-admin-*` window, so the hosted-admin windows that `open_web_admin`
creates on a remote HTTPS origin are refused every FOKS command by Tauri before
the command body runs. Tauri also refuses any app command from a remote origin
unless a capability with a `remote` entry grants it, and none does.

Four tests keep the three lists in agreement:

- `the_app_manifest_covers_exactly_the_registered_commands` compares the
  generated manifest with the `generate_handler!` names, so `build.rs` cannot
  miss a command or keep a removed one.
- `the_capability_grants_the_three_core_permissions_and_every_command` checks
  that the capability file allows exactly those commands and nothing outside
  `core:` other than them.
- `the_resolved_capability_reaches_only_main_and_the_registered_commands`
  resolves the generated capability and checks that `default` is the only
  capability and that it targets only `main` on the app's own origin.
- `only_the_main_window_on_the_app_origin_may_invoke_commands` builds Tauri's
  runtime authority from the generated context and asks it about every
  command: allowed for `main` on the local origin, refused for a
  `host-admin-*` window and for a remote origin.

Adding a command means adding it to `generate_handler!`, to `COMMANDS` in
`build.rs`, and as `allow-<command>` to the capability; the tests name the
list that is missing it. A command that takes `CommandState` also needs a
deadline class in `command_class` (`src/commands/deadline.rs`), checked by
`deadline_policies_name_exactly_the_commands_that_take_command_state`.

Each command also calls `require_main_window` itself, checked for every
registered command by `every_command_checks_the_main_window` in
`src/command_signatures.rs`, so that a capability granted too widely does not
by itself open a command to another window. Value-bearing commands are further
bounded by `require_unlocked`.

## Controls for value-returning commands

Controls protecting value-bearing commands, in order of evaluation:

1. `applock::unlocked_interval` at the top of every value-bearing command.
   Each agent call of the read is refused once the app locks, and the value
   is handed to the renderer, the clipboard, the browser or a file only
   inside `UnlockedInterval::publish`, which serializes that handoff with
   locking.
2. The native navigation policy in `src/navigation.rs`, so the window that may
   call these commands is only ever on FOKS's own origin.
3. The CSP `script-src 'self'` in `tauri.conf.json`.
4. This capability set, which grants the FOKS commands to the `main` window
   only.
5. `withGlobalTauri: false`, so the IPC surface is not published on a global
   object in a window that renders secrets.
6. One command returning one item at one version.

The first control is armed at process start whenever the operating system can
authenticate the desktop user. The renderer must read `app_lock_state` and
complete `unlock_app` before it loads agent or catalog data. A platform that
reports authentication unavailable starts unarmed so the UI cannot become
permanently inaccessible.

`read_item` is that sole value-returning command. `copy_item_value` performs
the same exact-version read but writes directly to the system clipboard;
`copy_item_field` does the same with one field of a login (password, user name
or website) selected in Rust; `open_item_url` selects a login's website the
same way and passes it to the platform's opener (`src/opener.rs`) only when
it is an http or https address; `download_file` sends bounded exact-version
chunks directly to a native-picked destination. None of them returns content
through IPC.

All Phase 3 mutation commands also call `require_unlocked`. A dropped source
path is accepted only when Rust observed a native event containing that one
UTF-8 path, and it is consumed once; multi-file drops authorize nothing. A
renderer cannot use the path-taking command as a general local file reader.
Rust rejects symlinks and non-regular sources and sends contents
to the local agent through bounded streaming frames. Native picker paths do not
cross IPC at all. Secret text and link targets necessarily arrive as mutation
arguments, are moved into zeroizing storage immediately, and are never echoed
in a response or log.

`require_main_window` in `src/commands/validation.rs` provides defense-in-depth
behind the app ACL by verifying that commands originate from the `main` window
label.

## Allowed window locations

`src/navigation.rs` registers a plugin whose `on_navigation` hook answers a
pure allowlist of whole origins — scheme, host and effective port compared
exactly, never by prefix:

| Origin | Packaged | Development |
| --- | --- | --- |
| `tauri://localhost` | allow | allow |
| `http://tauri.localhost`, `https://tauri.localhost` | allow | allow |
| `http://127.0.0.1:1421` | deny | allow |
| everything else | deny | deny |

`tauri://localhost` is what Tauri serves the embedded bundle from on macOS and
Linux; the `tauri.localhost` pair is wry's workaround form on Windows and
Android, allowed so that adding a target — or turning on `useHttpsScheme` —
is not a silent blank window. Everything else is refused: remote origins,
`file:`, `data:`, `blob:` and `javascript:` as a top-level destination, a
hostless URL, and any scheme Tauri did not register. A refusal cancels the
navigation and leaves the current page where it was; it logs scheme, host and
port, never a path, query or fragment, because those are attacker-chosen and a
window that renders secrets can put a value in one.

Whether the development origin is allowed is `tauri::is_dev()` —
`!cfg!(feature = "custom-protocol")` — and **not** `debug_assertions`, because
that feature is the same switch `tauri`'s own `get_app_url` reads when it
chooses between `build.devUrl` and the embedded bundle. This package declares
no `custom-protocol` feature, so `cargo build --release` still produces a
binary that loads the Vite server; `debug_assertions` would deny that binary
its own start page. `tauri build` turns the feature on for distributable
artifacts, which are exactly the builds where `http://127.0.0.1:1421` is
refused.

The CSP is the second line for the same boundary, not the first: `form-action
'none'`, `base-uri 'none'`, `object-src 'none'`, `frame-src 'none'` and
`frame-ancestors 'none'` close the mechanisms CSP does cover, but CSP does not
reliably govern every top-level navigation. `connect-src` is deliberately not
spelled out; `default-src 'self'` already governs it, and the effective policy
each packaged platform ends up with should be captured before that directive
is made more explicit.

`tauri.conf.json` configures only the `main` window, and the renderer has no
permission to create windows. Rust creates two kinds: a replacement `main`
window from the same configuration (from the macOS menu when no main window is
open), and the `host-admin-*` windows that `open_web_admin` opens on a server's
HTTPS admin origin. The navigation policy keeps a hosted-admin window on its
bound origin, and the app ACL above gives it no FOKS or core command.

## Clipboard platform difference

macOS copies include `org.nspasteboard.ConcealedType`, which asks cooperating
clipboard-history tools not to retain the value. Linux copies, on X11 and on
Wayland compositors with the data-control protocol, include the
`x-kde-passwordManagerHint` target with the value `secret`, which Klipper and
clipboard managers that follow its convention decline to record. Other Linux
clipboard managers can still capture the value, and X11 selection ownership
can disappear with the process. Linux therefore clears after 15 seconds
instead of 30; shutdown waits for one best-effort clear before exiting. For long-lived file content, use Download rather than clipboard copying.
On Linux environments without installed polkit actions, app lock reports
as unavailable.

## The permission decision, and how it is kept

The capability allowlist is restricted to the three required core permissions
and the FOKS commands, all for the `main` window.

- **Explicit permissions require explicit review.** An exact allowlist prevents
  new commands from being enabled implicitly during dependency updates.
- **Automated test verification.** Tests compare the capability file against the
  expected permission set, explicitly forbidding sensitive core permissions, and
  verify that resolved ACL manifests expand only to the permitted command identifiers.
- **Compiled features must not be mistaken for the control.** See the notes
  above: whether `tray-icon` or `devtools` is enabled decides what is compiled,
  not what the webview may call. The capability file remains the control.

If titlebar double-click-to-maximize is required, only grant
`core:window:allow-internal-toggle-maximize` specifically rather than the broader
`core:window:default` permission set.
