# Research note: cryptography and key management in foks-rs

Scope: `crates/foks-crypto`, `crates/foks-keystore`, `crates/foks-yubi`, the key-material types in `crates/foks-proto`, and the client-side flows in `crates/foks-client` that drive key rotation, pairing and recovery. All paths are relative to `/home/bnoland/projects/foks-rs`. Line numbers are from the tree as read on 2026-09-25.

The implementation targets wire compatibility with the upstream Go implementation `github.com/foks-proj/go-foks@v0.1.9`; almost every construction is explained in code comments as "the exact v0.1.9 construction", and the test suites compare against fixtures generated by Go (`crates/foks-snowpack/tests/fixtures/foks-v0.1.9/{account,invitations,realtime,signup,sso,user,user-mutations}`). That constraint explains many of the choices below: the Rust code often reproduces a Go idiom (NaCl `box.Precompute`, `argon2.IDKey`, msgpack-based canonical encoding) rather than choosing a textbook alternative.

A caution for the book: the project's own `docs/GUIDE.html` and `docs/INTRO.html` are useful but not always accurate about primitives. Three concrete discrepancies found while reading the code are listed in section 12.

---

## 1. The primitive toolbox

Everything in FOKS is built from a small set of primitives, chosen for compatibility with Go's `golang.org/x/crypto` and `nacl` packages. Dependency versions are pinned in the workspace `Cargo.toml` (lines 76-115): `ed25519-dalek 2`, `x25519-dalek 3`, `ml-kem 0.3.2`, `crypto_secretbox 0.1.1` (XSalsa20-Poly1305), `salsa20 0.10` (for HSalsa20), `chacha20poly1305 0.11`, `argon2 0.5`, `bip39 2`, `p256 0.13`, `sha3 0.12`, `sha2 0.10`, `hmac 0.12`, `yubikey 0.8`.

## 2. Typed hashing and "type IDs": domain separation everywhere

**Problem.** A key store signs, hashes and encrypts dozens of different object kinds. If two different objects could produce the same bytes, a signature on one could be replayed as a signature on the other. FOKS eliminates this class of bug systematically rather than case by case.

**How it works.** Every protocol object type has a 64-bit *type ID* constant (upstream calls them Snowpack type IDs). Examples, all in `crates/foks-proto/src/lib.rs:16-57`:

- `LINK_OUTER_V1_TYPE_ID = 0xc274_5284_af61_7745` (chain links)
- `SHARED_KEY_SEED_TYPE_ID = 0xa999_8e7a_59e8_ae25` (PUK/PTK seed boxes)
- `HEPK_TYPE_ID = 0x9c58_1bee_d36c_7e0c` (hybrid public key fingerprints)
- `HYBRID_SECRET_KEY_SHA3_PAYLOAD_TYPE_ID = 0x8a9e_3276_4726_2289` (hybrid KEM combiner)
- `TEMP_DH_KEY_SIG_TEMPLATE_TYPE_ID = 0xd51b_5d99_0285_023e`
- `BACKUP_SEED_TYPE_ID = 0xf4c4_fe8d_ff61_a6dc`
- `KEX_KEY_DERIVATION_TYPE_ID = 0x8d7b_c770_3f63_ad64`, `KEX_CLEARTEXT_TYPE_ID = 0xd2bc_e826_3ea1_dc0b`
- `KV_KEY_DERIVATION_TYPE_ID = 0xdbdf_2ba2_9c0d_e2cb`, `APP_KEY_DERIVATION_TYPE_ID = 0x9431_8317_830b_409b`

The type ID is prepended, big-endian, to the canonical encoding of the object before it is hashed, MACed, signed, or used as a nonce prefix:

- `prefixed_hash(type_id, object) = SHA-512/256(BE64(type_id) || object)` (`lib.rs:708-713`).
- `prefixed_hash_signable` additionally runs `foks_snowpack::validate_signable` on the bytes first (`lib.rs:719-722`), so only canonical encodings are ever hashed. (`validate_signable` rejects, for example, `array16` encodings with 16..31 elements, which must be `fixarray`; `crates/foks-snowpack/src/decode.rs:44-46`.)
- Signatures are computed over `BE64(type_id) || canonical_object` (`sign_ed25519_typed`, `lib.rs:746-757`); for P-256 the same message is first reduced with plain SHA-512/256 (`prefixed_hash_without_type`, `lib.rs:4442-4444`) because PIV hardware signs a 32-byte digest.
- HMACs use the same layout: `typed_hmac(key, type_id, object) = HMAC-SHA-512/256(key, BE64(type_id) || object)` (`lib.rs:564-570`).
- Secretbox nonces embed the type ID: the 24-byte XSalsa20 nonce is `BE64(type_id) || 16 random bytes` (`open_typed_secretbox` / `seal_typed_secretbox`, `lib.rs:620-654`). This is the "typed secretbox" idiom used throughout: the *purpose* of a ciphertext is baked into its nonce, so a ciphertext produced for one purpose cannot be decrypted under another purpose even with the same key.

Rust-only local constants deliberately use *different* IDs that never appear on the wire and are commented as such, e.g. `FEDERATION_PERMISSION_TOKEN_HASH_TYPE_ID = 0x45cf_32f3_7d38_a811` (`lib.rs:67-69`) and the chat-v2 domains derived as "first eight bytes of SHA-256 of the ASCII labels `foks.chat.v2.context-key` and `foks.chat.v2.encrypted-body`" (`crates/foks-crypto/src/chat_v2.rs:8-12`). That is a nice, teachable technique for allocating new domain separators without a registry.

**Signed "Future(T)" blobs.** Some objects are signed as a binary blob wrapping an inner canonical object (`sign_ed25519_blob`, `verify_blob`, `lib.rs:761-765`, `:4449-4462`). The comment at `lib.rs:4456-4459` explains why the inner bytes are validated too: checking only the outer binary wrapper "would allow every byte string, including Rust-only array16(16..=31) encodings". This is a forward-compatibility hook (an old verifier can check a signature on a blob it cannot parse) that had to be paired with strict canonicality checks.

**References.** The general technique is "domain separation"; see the discussion in RFC 8032 section 8.3 [VERIFY], the "Cryptographic Doom Principle" and, for typed hashing, the BLAKE3/TupleHash literature (NIST SP 800-185 for TupleHash/cSHAKE as the standardised analogue).

## 3. Entity IDs and the device key suite

**Problem.** Each key-bearing party (device, user, team, PUK, PTK, YubiKey, backup key, passphrase key, bot token, subkey) needs a stable identifier that is also a public key.

**How it works.** An `EntityId` is one type byte followed by a public key (`crates/foks-proto/src/entity.rs:9-80`). Type bytes are in `crates/foks-proto/src/lib.rs:59-73`: `USER=1`, `HOST=2`, `NAMED_TEAM=3`, `DEVICE=4`, `YUBI=8`, `HOST_MERKLE_SIGNER=10`, `HOST_TLS_CA=11`, `HOST_METADATA_SIGNER=12`, `SUBKEY=13`, `PUK_VERIFY=14`, `PTK_VERIFY=15`, `BACKUP_KEY=16`, `PASSPHRASE_KEY=17`, `BOT_TOKEN_KEY=19`, `AD_HOC_TEAM=20`. Software IDs are 33 bytes (type + Ed25519 public key); YubiKey IDs are 34 bytes (type + SEC1 compressed P-256 point, `lib.rs:3602-3605`).

A neat consequence: a *user ID* is literally the first owner PUK's verify key with the type byte overwritten (`uid_bytes[0] = ENTITY_USER`, `lib.rs:3368-3370`); team IDs are likewise derived from the admin PTK seed (`adhoc_team_id_from_admin_seed`, `named_team_id_from_admin_seed`, `lib.rs:1038-1051`). Identities are therefore self-certifying: whoever created the first key chose the ID, and the server cannot substitute one.

**Deriving a whole suite from one 32-byte seed.** Every software key (device, PUK, PTK, backup, passphrase, bot token, subkey) is a single `SecretSeed` (32 zeroizing bytes, `crates/foks-proto/src/key_material.rs:471-500`). `derive_key` (`lib.rs:4363-4376`) fans it out:

```
derive_key(seed, t, i) = HMAC-SHA-512/256(
    key = seed,
    msg = BE64(0xd35c_dcc9_5cae_f674) || snowpack([t, i? "4"->i : nil]) )
```

The derivation types used are (call sites collected by grep):

| t | purpose | site |
|---|---|---|
| 0 | Ed25519 signing seed | `lib.rs:3772`, `:798`, `:4342` |
| 1 | X25519 static secret | `lib.rs:3779`, `:4273` |
| 2 | symmetric "secretbox" key (seed chain, PPE PUK box, Yubi management key, federation view token) | `lib.rs:2290`, `:3686`, `:3721`, `:3933`; `passphrase.rs:385` |
| 4, index 0 and 1 | two 32-byte halves concatenated into the 64-byte ML-KEM seed `(d, z)` | `derive_mlkem_seed`, `lib.rs:4354-4361` |
| 5 | application-key root (KV, realtime chat) | `lib.rs:137`; `realtime.rs:21` |

(Type 3 is not used by the Rust code.) `derive_public_material` (`lib.rs:3771-3789`) computes the ID and the HEPK from these; `device_signing_key_pkcs8` (`lib.rs:3793-3802`) wraps the Ed25519 seed in a hand-built RFC 8410 PKCS#8 DER header so the *same* device key doubles as the mutual-TLS client certificate key.

This is not HKDF (RFC 5869) despite what GUIDE.html says; it is a single-step keyed HMAC with a typed, canonically encoded "info" argument. The comment in the derivation of ML-KEM shows why 64 bytes are needed: FIPS 203 `ML-KEM.KeyGen_internal(d, z)` consumes a 32-byte `d` and 32-byte `z`; the `ml_kem::Seed` type takes exactly that (`lib.rs:3782-3785`).

**References.** FIPS 203 section 6.1 (seed-based key generation), RFC 8410 (Ed25519 in PKCS#8), RFC 5869 (for contrast).

## 4. HEPK: hybrid encryption public keys, and the hybrid box

**Problem.** Keys distributed today must remain confidential against a future quantum computer ("harvest now, decrypt later"), but ML-KEM alone is young. FOKS requires *both* a classical and a post-quantum public key for every recipient.

**Data structure.** `Hepk { classical: DhPublicKey, mlkem768: Vec<u8> }` (`crates/foks-proto/src/identity/hepk.rs:9-20`), where `DhPublicKey` is `Curve25519([u8;32])` or `P256([u8;33])` and the ML-KEM-768 encapsulation key is 1184 bytes. The canonical encoding (`encode_hepk`, `lib.rs:4378-4400`) is a tagged-variant tree `[1, "1" -> [[1,"0"->classical],[1,"1"->mlkem]]]`; its fingerprint is `prefixed_hash_signable(HEPK_TYPE_ID, encoded)` (`hepk_fingerprint`, `lib.rs:3436-3438`). Chain links carry only the fingerprint; full HEPKs are uploaded alongside and checked against the fingerprint, which keeps links small while still binding the full key.

**The hybrid box** (`HybridBox`, `key_material.rs:13-19`): `{ kem_ciphertext (1088 bytes), dh_type (1 = Curve25519, 2 = P-256), sender_dh: Option<DhPublicKey>, nonce [u8;16], ciphertext }`.

Sealing (`seal_hybrid_payload`, `lib.rs:3208-3253`; the same steps appear inline in `seal_initial_puk_box` `lib.rs:3442-3486` and `seal_shared_key_boxes_with_sender` `lib.rs:2983-3072`):

1. **Classical agreement.** For software recipients: `dh_shared = HSalsa20(X25519(sender_static, receiver_pub), nonce = 0^16)`. The HSalsa20 step is the NaCl `crypto_box_beforenm` precomputation; the comment at `lib.rs:4315-4317` says explicitly "Go's nacl/box.Precompute applies HSalsa20 to the raw X25519 result; FOKS commits that NaCl precomputed key, not raw X25519, into the hybrid SHA3 payload." For P-256 recipients: raw 32-byte x-coordinate of ECDH (`lib.rs:2617-2622`; hardware in `hardware.rs:538-553`).
2. **Post-quantum encapsulation.** `ML-KEM-768.Encaps(receiver.mlkem768)`, using `encapsulate_deterministic` with a caller-supplied 32-byte `kem_message` so Go/Rust fixtures can be compared byte for byte (`lib.rs:2468-2475` explains that production fills it from the OS CSPRNG).
3. **Combiner.** `payload = snowpack([1, kem_shared(32), dh_shared(32), receiver_hepk, sender_dh])` (`hybrid_key_derivation_payload`, `lib.rs:2244-2259`) and `key = SHA3-256(BE64(0x8a9e_3276_4726_2289) || payload)`. Binding both public keys into the combiner is the standard defence against KEM ciphertext/key substitution in hybrid schemes.
4. **Symmetric seal.** `XSalsa20-Poly1305(key, nonce = BE64(payload_type_id) || nonce16, plaintext)`.

Opening (`open_hybrid_box`, `lib.rs:4175-4210`) checks `dh_type` against the receiver's classical key kind first, then reverses the steps. The receiver side is abstracted behind `HybridSecretDecapsulator` (`lib.rs:3560-3565`): `derive_dh_shared` and `decapsulate_mlkem768`. That trait is what lets software seeds, backup keys, passphrase keys and YubiKeys all open the same box format.

**Security reasoning.** If either X25519/P-256 or ML-KEM stays secure, `key` is unpredictable, because SHA3-256 is applied to the concatenation of both secrets. GUIDE.html section 3 states this "either primitive remains secure" argument.

**References.** FIPS 203; the IETF hybrid KEM combiner drafts (draft-ietf-tls-hybrid-design, draft-irtf-cfrg-hybrid-kems / X-Wing paper by Barbosa et al. 2024) [VERIFY exact draft names]; NaCl `crypto_box` documentation for the HSalsa20 precomputation; Bernstein, "Cryptography in NaCl" (2009).

## 5. Authenticated senders and the "temporary DH key" trick

**Problem.** A NaCl-style box with a static sender key authenticates the sender implicitly (only the two parties can compute the shared secret). But when the sender uses X25519 and the receiver uses P-256 (a software device boxing to a YubiKey, or vice versa), no static-static agreement is possible.

**Technique.** A box *set* (`SharedKeyBoxSet`, `key_material.rs:126-131`) contains many boxes for one mutation plus an optional `TempDhKeySigned { key, time, signature }` (`key_material.rs:231-254`). When the roster mixes curves, the sender generates one ephemeral key on the *receiver's* curve, uses it for every mismatched recipient, and signs `[box_id, [temp_key, time], [signer, host]]` under `TEMP_DH_KEY_SIG_TEMPLATE_TYPE_ID` with its long-term signing key (`seal_software_puk_boxes_mixed`, `lib.rs:2567-2689`, especially `:2668-2683`; the Yubi-parent mirror is `seal_yubi_puk_boxes`, `lib.rs:2786`). The receiver verifies that signature before accepting the temporary key as "the sender" (`authenticated_sender_dh`, `lib.rs:4148-4173`). The comment at `lib.rs:4156-4158` notes a compatibility subtlety: same-curve recipients in the same set ignore the temporary key, as Go does.

Every box in a set shares a random 16-byte `box_id`, and the signature over the temporary key includes it, so a temporary key cannot be transplanted between box sets.

## 6. PUK and PTK: generational shared keys

**Problem.** A user has many devices; a team has many members. Data must be readable by all of them, but revoking a device or removing a member must cut off future data.

**Structure.** A *per-user key* (PUK) and *per-team key* (PTK) are 32-byte random seeds, one per *role* and per *generation*. Roles are ordered `None < Member(visibility) < Admin < Owner` (`crates/foks-proto/src/role.rs:7-30`); members carry a signed 16-bit "visibility" level. Team creation makes four PTK seeds "ordered member-min, member, admin, owner" (`lib.rs:1054`, `:1237`). The seed for role *r* is boxed to every party whose role is at least *r* (`box_rotated_ptks` filters `rotation.role <= receiver.member.role`, `crates/foks-client/src/team/rotation/support.rs:527-531`; the device analogue filters `*role >= rotation.role`, `crates/foks-client/src/device.rs:760-763`). So an owner can open every role's key, an admin cannot open the owner key, and readers cannot open admin material.

Each PUK/PTK seed yields (via `derive_key`, section 3) an Ed25519 verify key (`ENTITY_PUK_VERIFY`/`ENTITY_PTK_VERIFY`) and an HEPK, so shared keys can both *sign* (team certificates, bearer-token challenges: `sign_shared_key_typed`, `lib.rs:792-804`) and *receive boxes* (PTKs are boxed to member users' PUK HEPKs, not to individual devices: comment at `lib.rs:2966-2968`, "The receiver entity is the owning user or team, not its verify key").

**The seed plaintext binds its context.** What gets encrypted is not the bare seed but `[[receiver, host], generation, role, seed]` (`shared_key_seed_plaintext`, `lib.rs:2261-2278`). On opening, `open_shared_key_parcel_with` (`lib.rs:4000`) and the seed-chain openers compare receiver, host, generation and role to what the verified chain says, and `Error::PukBinding` is raised on mismatch. A box for one role or host cannot be presented as another.

**Zeroization trick.** Decoding a seed plaintext uses `decode_with_redacted_trailing_seed` (`lib.rs:683-696`): the last 32 bytes are copied into zeroizing storage and overwritten with zeros *before* the generic msgpack decoder runs, so the secret never lands in an ordinary heap `Vec` owned by the value tree. The same idea appears in `team_removal_key_commitment` (`lib.rs:769-778`) and `BackupKey::derived_seed` (`backup.rs:159-172`), which hand-build the two-byte `bin8` header `[0xc4, len]` in a fixed zeroizing array instead of calling the encoder.

**Parcels.** A `PukParcel` (`key_material.rs:256-268`) is what a device fetches from the server: `{generation, role, hybrid, target, target_host, target_role, target_generation, sender, box_id, temp_dh_key, seed_chain: Vec<SeedChainBox>}`. The server assembles it from a stored box set plus the chain of older seeds (`PukParcel::from_box_set`, `key_material.rs:291-320`).

## 7. SeedChainBox: how rotation keeps old data readable

**Problem.** After a rotation from generation *g* to *g+1*, remaining members receive the new seed, but files and messages encrypted under *g*, *g-1*, ... must still open. Re-encrypting all data would be expensive and would still leave old ciphertexts around.

**Technique.** When rotating, the rotating party encrypts the *previous* seed under the *new* one:

```
SeedChainBox { generation: g, role,
  secret_box: XSalsa20-Poly1305(
      key   = derive_key(seed_{g+1}, 2),
      nonce = BE64(SHARED_KEY_SEED_TYPE_ID) || random16,
      msg   = [[party, host], g, role, seed_g]) }
```

(`seal_puk_seed_chain_box`, `lib.rs:2280-2305`). The server stores every chain box and returns the whole chain with a parcel. Opening walks the chain backwards (`open_shared_key_seed_chain`, `lib.rs:3917-3954`): start from the current seed, and for each box in reverse order require `box.generation == newer.generation - 1` and equal role, derive `derive_key(newer.seed, 2)`, open, check `[receiver, host, generation, role]`, push, repeat. The result is the list of all seeds, oldest first. A single hybrid box for generation *N* therefore unlocks generations 1..N with only symmetric operations, and each hop is authenticated so the server cannot splice in a foreign seed.

Client call sites: device revocation (`crates/foks-client/src/device.rs:796-806`), team member change (`crates/foks-client/src/team/rotation/mod.rs:1145-1157`, `:2715-2725`). Team chains have a special rule documented at `lib.rs:3956-3959`: "FOKS v0.1.9 creates one global chain per rotated PTK and binds its informational receiver field to the editor, then attaches that chain to every recipient parcel", so `open_team_shared_key_seed_chain` (`lib.rs:3960-3995`) checks host, generation and role but not receiver, and the caller must bind each seed to the team chain's public-key history.

**Invariant (forward secrecy on departure).** The evicted party holds seeds up to *g*, never receives a box for *g+1*, and *g+1* is a fresh random seed, so nothing encrypted under *g+1* is readable to them; existing members lose nothing because the chain lets them reach *g* from *g+1*. GUIDE.html section 1 calls this "Forward Secrecy via Generational Seeds". Note that this is forward secrecy in the group-messaging sense (post-compromise/future secrecy for the group), not the ephemeral-key sense.

**Rotation is signed by the new keys themselves.** In `make_software_puk_change_link` (`lib.rs:2411-2466`), each new PUK signs the accumulated signature stack *first*, in shared-key order, and the acting device signs last; the Yubi variant (`lib.rs:2329-2331`) explains "Each rotated PUK signs the accumulated stack first ... and the P-256 parent signs last as required by user-chain replay." This proves possession of the new seed at the moment the link is published.

## 8. Stacked signatures on chain links

**Problem.** Some transitions need the consent of several keys: the new device, the existing owner, a freshly introduced PUK, a YubiKey's delegated subkey.

**Technique.** A link's `signing_bytes(prefix)` is the canonical link plus the signatures already present; each signer appends over the previous ones (`make_yubi_eldest_link`, `lib.rs:3346-3426`: "owner PUK, delegated Ed25519 subkey, then the P-256 parent signature"). For KEX provisioning the new device signs with an empty prefix and the existing owner countersigns second (`countersign_software_kex_provision_link`, `finish_software_kex_provision_link`, `crates/foks-crypto/src/kex.rs:284-330`). Verifiers replay the stack in order. Because every signature covers the ones before it, the order itself is authenticated.

**ECDSA malleability note.** `verify_typed` accepts both low-S and high-S P-256 signatures (`lib.rs:4425-4430`): "to accommodate YubiKey PIV hardware, which does not normalize S values. Mutation replay protection relies on chain sequence, previous hash, and Merkle root bindings rather than signature malleability resistance." That is a clear, book-worthy example of choosing where a security property lives.

**Hidden chain locations.** Links commit to the *next* Merkle tree location with `tree_location_commitment = prefixed_hash_signable(TREE_LOCATION_TYPE_ID, bin(location))` (`lib.rs:724-729`), and subchains start at a hidden location `HMAC-SHA-512/256(seed, CHAIN_LOCATION_DERIVATION_TYPE_ID || [chain_type, nil])` (`subchain_tree_location`, `lib.rs:588-608`; server use at `crates/foks-server/src/services/generic.rs:182-184`). Similarly, usernames and device names are not published in the clear but as HMAC commitments with a random 16-byte key (`commitment(NAME_COMMITMENT_TYPE_ID, ...)`, `lib.rs:781-788`; `crates/foks-crypto/src/account.rs:22-24`). These are commitment schemes: hiding without the key, binding once published.

## 9. HESP: human-exact secret phrases (recovery kit and pairing code)

**Problem.** Two situations need a secret to pass through a human: the printed recovery kit (all devices lost) and the pairing code shown on one device and typed on another. Plain hex is error-prone; plain word lists are guessable by language models and, at short lengths, weak.

**Technique: a mixed-radix integer encoding.** A secret is treated as one big-endian integer and expanded, least significant digit first, in alternating radices 2048 (a BIP-39 word) and 2^k (a decimal number). The encoding loops `take_low_bits(11)` then `take_low_bits(13 or 8)` (`backup.rs:141-156`, `kex.rs:126-139`); decoding pushes the tokens back in reverse order with `push_bits` (`backup.rs:117-124`, `:308-323`). Word lookup uses `binary_search` in the sorted 2048-entry BIP-39 English list (`backup.rs:103-108`); KEX lowercases input first (`kex.rs:100`), the backup parser does not.

Parameters (constants in `backup.rs:16-23` and `kex.rs:22-27`):

| | Recovery kit (`BackupKey`) | Pairing code (`KexSecret`) |
|---|---|---|
| Seed bytes | 26 | 16 (`foks_proto::KEX_SECRET_BYTES`) |
| Tokens | 17: 9 words + 8 numbers | 13: 7 words + 6 numbers |
| Word bits | 11 | 11 |
| Number bits / range | 13, `0..8191` | 8, `0..255` |
| Entropy | 9*11 + 8*13 = 203 bits | 7*11 + 6*8 = 125 bits |
| Top-byte mask | `0x07` (208-203 = 5 unused bits) | `0x1f` (128-125 = 3 unused bits) |

Generation is `getrandom` into the array, then `seed[0] &= MASK` (`backup.rs:81-86`); parsing rejects nonzero unused high bits (`HighBits`) and arithmetic overflow, so every phrase corresponds to exactly one seed and vice versa (tested by round-trip and quickcheck tests, `backup.rs:326-350`, `:414-428`). A Go fixture test (`matches_official_go_backup_fixture`, `backup.rs:378-397`) pins the exact token order, and the KEX test gives a concrete example: the secret `[1; 16]` encodes as `cage 32 advice 4 letter 128 avoid 16 acoustic 2 doctor 64 amount` (`kex.rs:378-382`).

**Why numbers?** GUIDE.html section 9 argues three benefits: transcription cadence (alternating shapes reduce skipped/duplicated tokens), immunity to dictionary/LM attacks (104 of the 203 bits are numeric), and, for the recovery kit, no need for a checksum because the phrase is *exact* (every token is validated against a finite alphabet or range). Note that unlike BIP-39 proper, there is no checksum word; the "exactness" comes from the strict parser.

**From phrase to keys.** The recovery seed is *not* stretched: `derived_seed = SHA-512/256(BE64(BACKUP_SEED_TYPE_ID) || bin8(26-byte seed))` (`backup.rs:159-172`), then the standard device suite is derived with entity type `ENTITY_BACKUP_KEY` (`backup.rs:174-179`). The first word/number pair doubles as the public device name of the backup key (`device_name`, `backup.rs:150-157`). During normal operation the backup key is enrolled as a *device* of the appropriate role (`enroll_backup_key`, `crates/foks-client/src/recovery.rs:51-60`, `:139-157`), which means every later PUK rotation automatically boxes the new generation to the backup HEPK exactly like to any other device; the printed kit therefore stays valid across rotations without reprinting. Recovery then uses the backup key as the *existing* countersigner to provision a fresh device (`make_software_provision_link_from_backup_credential`, `seal_backup_puk_boxes_from_credential`, `recovery.rs:420-470`; `lib.rs:2040-2072`).

The KEX secret is expanded differently: `session_id = HMAC-SHA-512/256(secret, BE64(KEX_KEY_DERIVATION_TYPE_ID) || [0, nil])` and `secretbox_key = same with [1, nil]` (`KexSecret::keys`, `kex.rs:143-163`). The session ID is public (the server relay uses it to route packets); the secretbox key never leaves the two devices.

**References.** BIP-39 (word list only; FOKS does not use BIP-39's checksum or PBKDF2), Diceware/EFF word-list rationale for human-transcribable secrets [VERIFY], and the mixed-radix / "bignum to digits" encoding as a classic algorithm (Knuth TAOCP vol. 2, section 4.4 radix conversion).

## 10. KEX device pairing over an untrusted relay

**Problem.** Add a second device without ever moving the master seed through the server in the clear, and without either device having a pre-existing trust relationship with the other.

**Protocol** (`crates/foks-client/src/kex.rs`, messages in `crates/foks-proto/src/kex.rs:254-261`: `Error, Start, Hello, PleaseSign, OkSigned, Done`):

1. The provisioner (existing owner device) generates a `KexSecret`, shows the 13-token phrase, and publishes a `Start` packet (`publish_kex_provision_offer`, `kex.rs:135-148`).
2. The provisionee types the phrase, derives the same `session_id`/`secretbox_key`, generates a brand-new device seed locally, and sends `Hello { entity, hepk, device_name }`.
3. The provisioner builds a provisioning link naming the new device and its HEPK fingerprint, boxes the current PUK to the new HEPK (`seal_software_puk_boxes`, `kex.rs:332-345`), and sends `PleaseSign` with the unsigned link (plus, for owners, a compact passphrase package `KexPpe` so the new device can also serve passphrase login: `export_kex_ppe`, `passphrase.rs:301-315`).
4. The provisionee verifies the link only names *its* device with *its* HEPK fingerprint and a non-`None` role (`require_kex_device_binding`, `kex.rs:332-361`), signs first, and returns `OkSigned`.
5. The provisioner verifies that signature, countersigns, submits the mutation through its ordinary durable write-ahead path, and sends `Done`.

Every packet is `KexWrapperMessage { session_id, sender, sequence, payload: SecretBox }` where the payload is `XSalsa20-Poly1305(secretbox_key, BE64(KEX_CLEARTEXT_TYPE_ID) || nonce16, KexCleartext)` and the cleartext repeats `session_id`, `sender` and `sequence` so the relay cannot reorder or re-attribute packets (`KexKeys::seal/open`, `kex.rs:171-210`; test `kex_secretbox_rejects_wrapper_rebinding`, `kex.rs:403-430`). Each wrapper is additionally Ed25519-signed by the sending device (`sign_kex_wrapper`, `kex.rs:213-219`). The whole exchange has a five-minute budget (`DEFAULT_KEX_PAIRING_BUDGET`, tests at `kex.rs:789`).

**Why 125 bits is enough here.** The secret is single-use, short-lived, and the relay only sees ciphertext; an attacker must guess it online before the two devices finish. The recovery kit, by contrast, protects data at rest indefinitely and gets 203 bits.

## 11. Passphrase-protected encryption (PPE) and Argon2id

**Problem.** Some deployments want a password login (for example a browser or a first device with nothing else). Passwords are weak, so the design must stretch them and must keep a *history* of derived keys so old data remains reachable after a password change.

**Stretching** (`stretch`, `passphrase.rs:165-192`): Argon2id, version `0x13`, with `StretchVersion::V1 = (memory 64*1024 KiB = 64 MiB, iterations 3, lanes 2)`, output 64 bytes; `StretchVersion::Test = (512 KiB, 1, 1)` exists only for tests and is refused in production (`allow_test` gate). The 64-byte stream is split: bytes 0..32 become a `SecretSeed` from which a full device-style suite is derived with entity type `ENTITY_PASSPHRASE_KEY` (`:182`); bytes 32..64 are a local box key. The test at `passphrase.rs:539-562` pins the output to Go's `argon2.IDKey(raw, salt, 3, 64*1024, 2, 64)`. The salt is 16 random bytes; a zero salt is rejected (`:224`, `:339`).

**Data structure: the SKMWK list.** Each passphrase *generation* has a random 32-byte "SKMWK" (secret key material wrapping key); the whole list of them, tagged with `uid` and `host`, is encrypted under a fresh random session key (`SkmwkList`, `build_update`, `passphrase.rs:326-408`). That session key is then boxed twice:

- a **passphrase box**: a hybrid box (section 4) from an *ephemeral* sender to the passphrase-derived HEPK, carrying `{generation, session_key}` (`:361-379`);
- a **PUK box**: a typed secretbox under `derive_key(owner_puk, 2)` carrying `{generation, session_key, passphrase_public_key}` plus the PUK's `generation` and `role = OWNER` beside it (`:381-400`).

Consequences: a passphrase change appends a new SKMWK and re-encrypts the list (`change_passphrase_with_puk`, `:243-264`); an owner PUK rotation can re-seal the parcel *without the plaintext passphrase* because the PUK box path opens it (`rotate_passphrase_for_puk`, `:266-287`, tested at `:565-611`); login decrypts via the passphrase box and signs the registration challenge with the passphrase key (`PassphraseLoginCredential`, `:412-455`). The keyring itself is zeroized on drop (`:78-82`).

**References.** RFC 9106 (Argon2), OWASP Password Storage Cheat Sheet (Argon2id parameter guidance) [VERIFY].

## 12. YubiKey PIV integration: hardware P-256 plus derived ML-KEM

**Problem.** A hardware token should hold the device's private keys, but PIV cards only offer RSA/ECC; there is no on-card ML-KEM.

**Technique.** A FOKS Yubi credential uses two PIV "retired" slots in `0x82..=0x95` (`SlotId::MIN/MAX`, `crates/foks-yubi/src/provider.rs:19-20`), both generated on-card as `AlgorithmId::EccP256` with configurable PIN/touch policies (`hardware.rs:150-176`):

- **Signing slot**: identity (`ENTITY_YUBI` + compressed point) and ECDSA signatures over the 32-byte SHA-512/256 prehash (`sign_sha512_256`, `hardware.rs:377-392`). `sign_yubi_typed` (`lib.rs:3751-3763`) immediately re-verifies each hardware signature.
- **PQ slot**: the card computes ECDH *of the PQ slot with its own public key* (`ecdh(yubikey, pq_slot, pq_public_key)`, `hardware.rs:332`, `:364-371`). The resulting 32-byte x-coordinate (`pq_self_secret`) is a card-bound secret that the host cannot obtain without the card and PIN. The host feeds it through `derive_mlkem_seed` to obtain a deterministic ML-KEM-768 key pair (`derive_yubi_public_material`, `lib.rs:3595-3618`; `yubi_mlkem_decapsulate`, `lib.rs:3621-3626`). The HEPK is `Hepk::yubi(signing_pubkey, mlkem_pubkey)`; note the classical half is the *signing* slot's key, used for ECDH via `derive_dh_shared` (`hardware.rs:344-356`).

The trait doc at `lib.rs:3567-3573` is candid about the limitation: "The v0.1.9 compatibility construction necessarily materializes derived ML-KEM state in the process and must not be described as hardware-native PQ security." The PQ slot's public key is identified by `yubi_pq_key_id = prefixed_hash_signable(ECDSA_COMPRESSED_PUBLIC_KEY_TYPE_ID, bin(pubkey))` (`lib.rs:3588-3591`).

**Delegated subkey.** Because a P-256 card cannot do mutual TLS for the Rust client conveniently and every RPC would otherwise need a touch, a Yubi parent enrolls a software Ed25519 *subkey* (`ENTITY_SUBKEY`) for mTLS. The subkey seed is sealed to the parent in a hybrid self-box (`seal_yubi_subkey_box`, `lib.rs:3636-3676`: P-256 self-DH plus ML-KEM to the parent's own HEPK, payload type `SUBKEY_SEED_TYPE_ID`, cleartext `[parent, subkey, seed]`), stored on the server, and re-opened by the card at login (`open_subkey_box`, `lib.rs:4123-4146`). The eldest link stacks PUK, subkey and parent signatures (`lib.rs:3405-3425`). The PIV management key (24 bytes) can also be escrowed under the PUK with a typed secretbox (`seal_yubi_management_key`, `lib.rs:3681-3712`; payload `crates/foks-proto/src/yubi.rs:74-79`).

**Operational safeguards** (`hardware.rs`): every operation reopens the card by serial and re-checks both slot public keys (`verify_locator_slots`, `:479-482`); on first use it proves slot possession by signing `SHA-512/256("foks-yubi-slot-binding-v1")` (`prove_slot`, `:526-536`); provisioning refuses non-empty slots and refuses firmware < 5.2.3 that cannot report slot metadata (`ensure_slot_empty`, `:446-458`); a process-wide mutex serialises APDUs (`:25-31`). A deterministic mock provider (`crates/foks-yubi/src/mock.rs`) implements the same traits for integration tests, including injected fail points.

**References.** NIST SP 800-73-4 (PIV), Yubico PIV documentation for retired key slots 0x82-0x95, SEC 1 (compressed point encoding), FIPS 186-5 (ECDSA).

## 13. Application keys: KV vault and chat

**Derivation tree** (`derive_kv_keys`, `lib.rs:136-160`): `app_key = derive_key(seed, 5)`; `kv_app = typed_hmac(app_key, APP_KEY_DERIVATION_TYPE_ID, [0, "0"->0])`; then `mac = typed_hmac(kv_app, KV_KEY_DERIVATION_TYPE_ID, [1, nil])` and `box_key = ... [2, nil]`. Realtime chat uses the same root with app index 1 and a further per-purpose HMAC (`derive_realtime_keys`, `crates/foks-crypto/src/realtime.rs:17-48`), pinned to Go fixtures `realtime/key-{1,2,3}.bin`. GUIDE.html's "app index 5 (kv_app)" is a slight misdescription: 5 is the derivation type for the application root; KV is app 0 and realtime app 1 under it.

**Three-level KV key hierarchy.** The PUK/PTK-derived `box_key` encrypts only *seeds*: a per-directory seed (`seal_directory_seed`, nonce suffix = directory ID, `lib.rs:329-341`) and a per-large-file seed (`seal_file_seed`, bound to `[object_id, version, seed]`, `:369-405`). Directory seeds derive their own MAC/box pair (`derive_seed_kv_keys`, `:546-562`) used for dirent names and dirent bindings; file seeds directly key chunk encryption. So rotating a PUK re-encrypts only a handful of seed boxes, not the data.

**Deterministic nonces from identities.** Small files use the 16-byte object ID as the nonce suffix (`seal_small_file`, `:343-368`, with the doc warning that IDs "must be freshly generated for every distinct plaintext under this key"); large-file chunks use `nonce = SHA-512/256(KV_CHUNK_NONCE_PAYLOAD_TYPE_ID || [file_id, offset, final])[..24]` (`seal_kv_chunk`, `:445-479`). A reader recomputes the nonce from the offset it *asked for*, so a server that swaps chunks fails authentication (`open_kv_chunk`, `:512-545`). Random nonces are used where the identity is not unique enough (dirent names, file seeds).

**Length hiding by padding.** Small payloads are padded to `max(32, len).next_power_of_two()` (`seal_typed_secretbox`, `:647-650`); chunks to a power-of-two base plus the msgpack `bin` header overhead (`kv_chunk_padded_length`, `:656-674`); the padding must be all zeros after the canonical value (`require_zero_padding`, `:676-681`).

**MAC-then-box for structure.** Directory roots and dirents carry HMAC "bindings" over `[party, key, root, version]` and the dirent fields (`bind_root`, `bind_kv_dirent`, `:163-179`, `:436-443`) so the server cannot roll back a directory version or re-parent an entry, even though it can see the ciphertexts.

**Chat v2 context keys** (`chat_v2.rs:14-20`): a per-message key `HMAC(seed, CONTEXT_KEY || RtChatContext)` where the context includes host, team, channel, actor, operation ID, key role/generation and purpose. The test `every_context_field_is_authenticated` (`:60-140`) flips each field and checks decryption fails; this is "authenticated context by key derivation" rather than by AAD, chosen because XSalsa20-Poly1305 has no AAD input.

## 14. Team-specific constructions

- **Removal keys.** Each member gets a random 32-byte removal key. Its commitment `prefixed_hash_signable(TEAM_REMOVAL_KEY_TYPE_ID, bin8(key))` is published in the member's chain link (`team_removal_key_commitment`, `lib.rs:769-778`); the key itself is hybrid-boxed twice, to the admin PTK and to the member (`seal_team_removal_key`, `lib.rs:3078-3132`, with metadata `{team, host, member, member_host, source_role, destination_role, team_sequence}`). A removal is accompanied by `HMAC-SHA-512/256(removal_key, TEAM_REMOVAL_MAC_PAYLOAD_TYPE_ID || payload)` (`make_team_removal_proof`, `lib.rs:1848-1864`), which the server stores (`crates/foks-server/src/services/team_loader.rs:628`). Inferred purpose (consistent with upstream FOKS): a removed member, who can no longer load the team chain, can still verify that their removal was authorised by someone holding the key. [VERIFY against go-foks documentation.]
- **Team certificates / invitations** (`crates/foks-crypto/src/invitations.rs`): a certificate payload `{team, current admin PTK verify key + HEPK fingerprint, time, hepk, name}` is signed by the current PTK and, if the generation is not 1, also by the *first* PTK, so an invite created by an old link still chains to the team's original identity (`:49-83`). The invite that users share is just `{host, hash = prefixed_hash_signable(TEAM_CERT_TYPE_ID, cert)}` (`:11-17`). Remote join requests are hybrid-boxed to the certificate's HEPK (`seal_remote_join_request`, `:86-107`).
- **Federation view tokens** are secretboxed under `derive_key(ptk, 2)` (`seal_team_remote_member_view_token`, `lib.rs:3716-3733`), and their storage identity is a one-way local hash (`federation_permission_token_hash`, `lib.rs:732-734`).

## 15. Local storage: keystore, protected store, state archive

These are Rust-only formats (nothing here is on the FOKS wire), and they use XChaCha20-Poly1305 with AAD instead of NaCl secretbox because AAD lets the record *name* be authenticated.

**`foks-keystore` records** (`crates/foks-keystore/src/lib.rs`): file `<key>.fks` = `MAGIC "FOKSKS\0\x01" (8) || nonce (24, random) || XChaCha20-Poly1305(master_key, nonce, value, aad)` with `aad = "foks-keystore-record-v1" || BE64(len(key)) || key` (`record_aad`, `:642-648`; `encode/decode`, `:433-483`). Limits: 16 MiB per record, 128-byte keys restricted to `[A-Za-z0-9._-]` and not `.`/`..` (`validate_key`, `:620-633`). Writes are crash-safe: random `.tmp-` file with `O_NOFOLLOW` and mode `0600`, `fsync`, rename, `fsync` directory (`:487-502`, `:704-714`). The 32-byte master key comes from the platform keyring (macOS Keychain generic password under service `com.aka.foks.client.<namespace>`, `:172-174`; Linux freedesktop Secret Service with `EncryptionType::Dh` D-Bus session encryption, `:262-264`) or from an owner-only key file for headless use (`create_master_key_file`, `:562-575`). A thread-local "unattended" flag (`without_user_interaction`, `:74-84`) lets background agents fail fast instead of popping keychain prompts. The record names the app uses are `master-key-v1`, `state-root-v1`, `native-state-v1` (`crates/foks-client-app/src/lib.rs:70-71`, `checkpoint.rs:12`).

**Protected mutation store** (`crates/foks-client/src/protected_store.rs:14-19`): same pattern with magic `FOKSPMS\x01`, AAD domain `foks-protected-mutation-store-v1`, and a hashed filename via `KEY_NAME_TYPE_ID`; its job is to make multi-step mutations (which hold fresh PUK seeds and box randomness) resumable after a crash without ever persisting plaintext.

**State-transfer archive** (`crates/foks-keystore/src/state_archive.rs`): a streaming, chunked, authenticated container for moving a whole client state between machines. Key: 32 random bytes shown as `FOKS-STATE-TRANSFER-V1:<64 hex>` (`:11`, `:34-65`). Per-archive cipher key `SHA-256("foks-state-transfer-key-v1\0" || key || header[9..41] || header[41..57])` (`:76-92`); nonce = 16-byte archive salt || 64-bit frame counter (`:94-99`); every frame's AAD is the full 73-byte header plus `[counter, entry, chunk, length, finality]` (`:100-114`), so truncation, reordering, duplication and cross-archive splicing all fail (`tests :442-512`). Chunks are 1 MiB, at most 8192 entries, 8 GiB total, with a SHA-256 trailer.

**Go interop reader** (`crates/foks-go-interop/src/lib.rs`): reads the upstream Go client's secret store (`foks-secrets`), including its macOS-keychain-wrapped XSalsa20 bundles, so a Rust client can adopt a Go device identity.

## 16. Small but notable techniques

- **Deterministic randomness injection.** Every sealing function takes explicit `PukBoxRandomness { kem_message, nonce }` / `InitialPukBoxRandomness` values instead of calling the RNG internally (`lib.rs:2468-2527`). Production fills them with `getrandom`; tests replay Go fixtures. This is what makes byte-exact differential testing against Go possible.
- **Redacted `Debug`.** Every secret type (`BackupKey`, `RecoveryPhrase`, `KexSecret`, `Passphrase`, `PassphraseKeyring`, `BotToken`, `StateTransferKey`, `YubiManagementKeyBoxPayload`) implements `Debug` as `"[REDACTED]"`, and `Zeroizing` wrappers are used pervasively.
- **Bot tokens** (`crates/foks-crypto/src/bot_token.rs`): 26 random bytes = 3-byte public name (5 base-36 chars) + 23-byte secret (base-62), text form `nnnnn.<31 chars>`; seed = `SHA-512/256(BOT_TOKEN_SEED_TYPE_ID || bin8(26))`, then the ordinary suite with `ENTITY_BOT_TOKEN_KEY`.
- **OIDC binding** (`crates/foks-crypto/src/sso.rs`): the OAuth `nonce` is the typed hash of a binding object, PKCE uses `S256` (RFC 7636) with a 32-byte verifier, and the ID token is bound to the device by an Ed25519/P-256 signature so the IdP never learns key material.
- **Capability MACs and registration challenges** (`capability_mac`, `lib.rs:583-585`; server use at `crates/foks-server/src/services/registration.rs:200-204`): the server hands out `HMAC(server_key, type_id || payload)` tokens it can later re-verify statelessly, constant-time (`verify_mac`, `:572-578`).

## 17. Discrepancies between the docs and the code (worth flagging in the book)

1. `docs/INTRO.html` and `docs/GUIDE.html` say the 17-token recovery kit is "stretched via Argon2id (64 MiB memory, 3 iterations)". In the code the recovery seed is only typed-hashed with SHA-512/256 (`backup.rs:159-172`); Argon2id with those parameters is applied to *user passphrases* (`passphrase.rs:165-192`). With 203 bits of entropy, stretching would add nothing, so the code is right and the doc is loose.
2. GUIDE.html describes the hybrid combiner as "SHA-512/256 (or HKDF)"; the code uses SHA3-256 over a typed payload (`lib.rs:3231-3234`), and the key hierarchy is typed HMAC-SHA-512/256, not HKDF.
3. GUIDE.html's key-family table says the KV keyset MAC is "HMAC-SHA256"; it is HMAC-SHA-512/256 (`lib.rs:564-570`).
